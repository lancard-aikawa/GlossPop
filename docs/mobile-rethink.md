# 携帯前提で引き直す（→ GlossPopApp）

**結論: 本体には足さず、GlossPopApp という別プロジェクトにする。**
決定そのものは [design-notes.md](design-notes.md) にあり、ここは**そこへ至る検討の
記録**。[open-questions.md](open-questions.md) にあった「複数端末での共有」の続きで、
あちらからは畳んだ。

以下は**書いた順に積んである**ので、後の節が前の節を上書きしている箇所がある
（ストレージの置き場所がいちばん動いた）。**追記のほうが新しい。**

## 決まったこと

**主戦場はコンシューマ。ビジネス用途ではない。**

これで下流がだいぶ決まる（→ 末尾の「コンシューマに決めた結果」）。要点だけ先に:

- **ネタバレ抑止は生き返る**（社内路線なら捨てるはずだった）
- **点検は落ちる。統合は画面ではなく登録時の警告になる**
- **ストレージを用意させる案（2）は既定にできない** —— 個人辞書（案 3）が既定

**課金の軸は 2 つ。**（→ 末尾の「課金」）

- **グループ機能** —— 人数と総量で毎月
- **LLM** —— キーを用意できない人にこちらのキーを使わせて毎月。
  知っている人は自分のキーで無料

これで「ストレージはこちらが持たない」が**3 つに割れる**（個人＝端末 /
グループ＝こちらがホスト / 控え＝利用者のストレージ）。**持たないのは控えだけ。**

**さらにその後、オンラインを主に決めて個人辞書もサーバへ動いた**（→「オンラインが主」）。
端末に残るのは キャッシュ + 設定 だけで、「設定ゼロ」は匿名アカウントで保つ。

## なぜ引き直すのか

共有だけを足そうとすると、**判断が残りすぎる**。ローカル辞書は残せるか、外のエディタ
編集はどこまで守れるか、`.glosspop` の祖先探索はどうなるか —— どれも「たぶん残せる」で
先延ばしにできてしまい、そのぶん設計が揺れる。

**携帯前提にすると、この手の判断が全部「無い」で片付く。** 逃げ場が無いのが利点。

ただし新しい難問が 1 つだけ増える。**オフラインと同期**。→ **オンラインが主に決めた**
（下記）。

## 案（5 つ）

### 1. ユーザグループ機能

そのグループでのみ共有される辞書を作る。

**いまの `scope` の素直な延長**なので、形は既にある。ref はグローバルが
`<カテゴリ>/<slug>`、ローカルが `.local/<カテゴリ>/<slug>` で、**カテゴリ名は「.」で
始められない**から衝突しない —— ここに `.g/<グループ>/<カテゴリ>/<slug>` を足すだけで
同じ規則に乗る。`find_by_surface()` が最初からリストを返すので、**個人辞書と
グループ辞書に同じ用語名があっても壊れない**（そのために作った性質がそのまま効く）。

決めること 3 つ:

- **`relations.resolve()` の絞り込み順。** いまは 書き手のカテゴリ → 同じ辞書 → 全体。
  グループを足すと 自分のグループ → 個人 → …… の順を決める必要がある。
  **吸収は 1 か所（`resolve()`）のまま**を崩さないこと
- **辞書をまたぐ関係を許すか。** 個人のエントリからグループのエントリへ関係を張れると
  便利だが、**グループを抜けた瞬間に行き先が消える**。`former_refs` の転送は同じ辞書の
  中の話なので、これは救えない。許すなら「相手が見えなくなった関係」の見せ方が要る
- **誰が書けるか。** 全員が書けると多書き手の衝突が戻る。とくに**カテゴリ改名と統合は
  ディレクトリごと動かす操作**なので、同時に走ると壊れる。**書けるのは持ち主だけ・
  他は読むだけ**から始めるのが安全（「書き込みは持ち主 1 人のままにして引く側だけ
  開く」と同じ線）

### 2. ストレージはグループに用意させる（こちらは持たない）

**5 案の中でこれが親。** ここを決めると他が従属して決まる。

> **追記（課金の軸を決めた結果）。** 「こちらは持たない」は**3 つに割れた** ——
> グループ機能で総量課金するなら、**グループ辞書はこちらがホストする**ことになる。
>
> | | 置き場所 | 費用 |
> | --- | --- | --- |
> | 個人辞書 | ~~端末~~ → **こちらがホスト** | 無料・匿名アカウント |
> | グループ辞書 | **こちらがホスト** | 人数と総量で課金 |
> | 控え | 利用者の Drive など | 無料 |
>
> **さらに追記（オンラインを主に決めた結果）。** 個人辞書も**サーバへ動いた**
> （→「オンラインが主」）。端末に残るのは キャッシュ + 設定 だけ。
> 「設定ゼロ」は**匿名アカウント**で保つ。
>
> **持たないのは控えだけ。** これなら初回起動に OAuth が出ない。
> 以下は「一切持たない」前提で書いた検討なので、**照合を端末側でやる話は
> グループ辞書には当てはまらない**（サーバが中身を持つので `Linker` を渡せる）。
> ただし**個人辞書は端末にしか無い**ので、結局どちらかで端末側の照合は要る。

#### Drive は控え専用。本番の置き場にはできない

**下の表で Drive を「ファイル置き場だから 1 用語 1 ファイルがそのまま乗る」と
書いたが、それは形式の話で、アクセス特性は逆。** 訂正しておく。

- **`Linker` は全エントリが揃わないと組み立てられない**（表記の木を作るため）。
  「必要な 1 件だけ取る」ができない
- `store._signature()` は `os.scandir` **1 回**で全件の mtime とサイズを得ている
  （3000 語 6ms。`Path.glob` + `stat()` だと 33ms）。Drive API では 3000 件の一覧に
  ページング数回、中身にさらに N 回。**「1 用語 = 1 Markdown」はローカルディスクでは
  最高で、リモートのファイル API では最悪の形**
- 本番の置き場にするなら結局「起動時に全部落とす」ことになり、**それはもう同期であって
  置き場ではない**

#### 端末側の住み分け

| | 置き場所 |
| --- | --- |
| 設定（テーマ・文字サイズ・読書位置） | SharedPreferences / localStorage |
| 辞書本体 | SQLite / IndexedDB |
| 控え | Drive など |

**SharedPreferences 相当に辞書を置かないこと。** あれは数 KB 想定の設定用キー値
ストア。現行も同じ分け方（設定は localStorage、辞書はファイル）。

#### 同期するなら単位は zip

**3000 ファイルを同期しない。** `archive.py` の `export_bytes()` が既に zip を作り、
**控えは書き出しと同じ zip**（そのまま取り込み直せる）という約束もある。同期の単位を
これにすれば**衝突の規則も既にある** —— 併合は「取り込む側が勝つ」の 1 行で、
`updated_at` の新しいほうに変えない（時計のずれた端末が 1 台あると静かに古いほうが
勝つ）という判断まで済んでいる。

#### 自動化の引き金は `persist()` が false のとき

手動の控えで足りないのはそこだけ。**保護されていないと分かっているのに手動任せは
弱い。Drive API を実装する引き金はここ**、という整理が素直。

なお控えのみ＝**端末を替えたときの引き継ぎは手動復元だけ**になる。これ自体は
「引き継ぎも保存先の移動も元を消さない」という既存の方針と整合する。

利点ははっきりしている —— 保管費が要らない、他人のデータを預からない、規模が増えても
こちらの負担が増えない。**欠点もはっきりしている**: 用意させた時点で、用意できない人が
全部落ちる。S3 を個人に用意させるのは、ほぼ確実に壁になる。

候補と評価:

| 置き場所 | 向いている相手 | 備考 |
| --- | --- | --- |
| **Google Drive / Dropbox（OAuth）** | 一般の人 | **すでに持っている**のが最大の利点。アプリ専用フォルダの権限なら他は見えない |
| **Cloudflare R2** | 多少わかる人 | S3 互換で**転送料が無料**。AWS より設定がだいぶ楽 |
| **GitHub リポジトリ** | エンジニアの集まり | 1 用語 = 1 Markdown なので**そのまま乗る**。版管理も差分も無料で付く |
| **S3 / B2** | 会社 | 個人には手続きが重い |

**Drive / Dropbox / GitHub はどれもファイル置き場**なので、書き出した形をそのまま
置ける。既定を Drive、わかる人向けに R2 と GitHub、あたりが素直。

**ただし「1 用語 = 1 ファイルのまま置ける」とは考えないこと**（→ 上の
「Drive は控え専用」）。**置くのは zip 1 つ。** GitHub だけは例外で、1 ファイルずつ
置く意味がある（差分と版が付く）が、それは**エンジニアの集まりに限った話**なので
既定の設計をそちらに引っ張らせない。

**ただし、ここに最大の帰結がある。**

サーバが辞書の中身を持たない以上、`Linker` に全エントリを渡せない。つまり
**照合は端末側で走る**ことになり、[../glosspop/linker.py](../glosspop/linker.py) を
JS へ移すことになる。付いてくるものが多い:

- **表記の木**（`_trie` / `_branch` / `_fold`）と 3 つの規則（続きのある枝が先・
  枝のキーは小文字・境界チェックは先頭が根で末尾が終端）
- **`(?-i:…)`** のインライン修飾子と**ルックビハインド**。ブラウザで対応が割れるので、
  そのままは配れない。組み立て直しになる
- `INLINE_TAGS` / `SKIP_TAGS` の走査。ただし端末側なら**文字列走査ではなく DOM を
  歩ける**ので、むしろ素直になりうる

**移すなら片方を消すこと。** 2 か所に置いた瞬間、片方で直してもう片方で直し忘れて
「同じ辞書なのに違う語がリンクになる」という、**画面を見ても分からない壊れ方**をする
（**照合を 2 か所に書かない** —— 共有を検討し始めた時点で先に決めてあった約束が、
ここで効く。→ [design-notes.md](design-notes.md)）。

逆に言えば、照合が端末側に行くなら**サーバの仕事は AI の代理とグループの認証だけ**に
なる。かなり安いサーバで済む。**これは悪くない着地**なので、選択肢として真面目に置く。

### 3. 個人辞書（端末に保存するだけ・誰にも見せない）

**いちばん安く、いちばん最初に作れる。** 案 2 で照合が端末側に行くなら、個人辞書は
サーバをまったく必要としない（IndexedDB に置くだけ）。

**最初の版をこれ 1 つで出せる**のが利点。グループもストレージ連携も無しで、
「読む・引く・登録する」が完結する。案 1 と 2 はその上に足す形になる。

### 4. Web 中心（Web アクセスの充実化） — **実サイトで確かめた**

**結論: 読める。Web 中心でいける。** 最大の懸念だった なろう・カクヨムの遮断は無い。

| サイト | 本文（タグ除去後） |
| --- | --- |
| 青空文庫（坊っちゃん） | 89,216 文字 |
| なろう（無職転生 プロローグ） | 5,621 文字 |
| カクヨム（エピソード） | 2,778 文字 |
| Wikipedia ja | 20,066 文字 |
| はてなブログ | 20,137 文字 |
| note.com | **0 文字**（SPA。正しくエラーになる） |

**ルビも正しく処理されていた** —— `ruby` 3,042 個が残って `rt` は 0 個。読みが地の文に
混ざる例の壊れ方（`銀河ぎんが`）は起きていない。

**カクヨムは作品ページから `/works/<id>/episodes/<id>` を辿れる**ので、連載を順に読む
導線が素直に作れる。

#### この確認で見つかった現行アプリのバグ 2 件（直した）

- **青空文庫が文字化けしていた。** ヘッダに charset が無く
  (`Content-Type: text/html`)、`httpx` の `response.encoding` は charset が無いと
  **utf-8 に倒れる**ので、`errors="replace"` で化けたまま読めていた。meta charset は
  `Shift_JIS` と書いてある。**ファイル経路で既に踏んだ罠と同じもの**で、URL 経路には
  その修正が入っていなかった → `documents.decode()` に `declared` を足して合流させた
- **SPA が無言で空になっていた。** note.com が返すのは空の div だけ（89 文字）で、
  `if not text.strip()` を**すり抜けて真っ白な画面になっていた** → タグを外して
  から判定する

**残っている限界**（元からで、今回は直していない）: `charset=iso-8859-1` と嘘を
名乗るページは latin-1 が何でも復号できてしまうぶん、化けたまま通る。

携帯にはファイルという概念が薄いので、読むものは Web になる。これは正しい。
そして**半分できている** —— [../glosspop/fetcher.py](../glosspop/fetcher.py) /
[../glosspop/htmlclean.py](../glosspop/htmlclean.py) /
[../glosspop/sites.py](../glosspop/sites.py) と URL 辞書がすでにある。

足すべきなのは**入り口**のほう:

- **共有シート**（ブラウザの「共有」→ GlossPop）。携帯での自然な入り口はこれ。
  URL を投げ込めば読める、が最短
- **アプリ内リーダー**で読む。ブラウザ拡張は携帯では実質作れない（iOS は苦しく、
  Android も Firefox だけ）ので、**中で読む**しかない

覚悟しておくこと:

- **青空文庫は遅い**（実測 15.2 秒。`clean_html` は 0.08 秒なので**全部ネットワーク**）。
  `FETCH_TIMEOUT` が 20 秒なので余裕が無く、**携帯の回線だと超える**
- `htmlclean` は**実際のサイトで確かめないと壊れているのが分からない**
  （`<input>` を `DROP_TREES` に入れて本文が全部消えた件、2 つめの `<article>` が
  1 つめを消した件。どちらも `example.com` では気付けない）。Web 中心にするなら、
  この手の事故は**確実に増える**。実サイトの回帰テストが要る
- ログインの要るサイト・SPA・取得を拒むサイトは読めない。**読めないことを黙らない**
  （打ち切りを必ず返すのと同じ約束）

### 5. デコレーション路線（シール）

Web サイトを日記帳のシールのように飾る。用語の登録＝シールを貼る。

**技術的な芯はもう出来ている。** `<a class="gloss-link">` は「本文の**この表記の
ところだけ**に飾りを乗せる」ことそのもので、それを正確にやるのが `Linker` の仕事。
**難しいほうが済んでいて、残っているのは見た目**という珍しい形。

さらに 3 つ噛み合う:

- **シール = 用語ごとの画像**は、[open-questions.md](open-questions.md) の 7 番
  そのもの。置き場所（`<辞書>/images/<slug>.<拡張子>`）も、配る／受け取る口の規則も
  設計済み。**別々に考えていた 2 つが同じ機能**だった
- **相関図は日本語圏では「キャラ相関図」**という既に通じる概念で、
  [../glosspop/static/ego.js](../glosspop/static/ego.js) の中心の図はまさにあの形。
  `samples/坊っちゃん` が既に人物の相関図になっている
- **収集**は一覧ページがそのまま使える

注意しておくこと:

- **「女性向け」は設計の指示にならない。** 実際に効くのは **装飾・収集・共有** の
  3 つで、それを作った結果として誰が来るかは後から分かる。狙いを「誰向け」ではなく
  「何が楽しいか」で書いておくこと
- **辞書としての正確さと衝突しない。** シールは見た目の層なので、`Linker` の規則を
  緩めないこと。「かわいいから多めにリンクする」に倒すと、`API` が `rapid` に当たる
  例の壊れ方に戻る

## コンシューマに決めた結果

社内共有路線とデコ路線は同じアプリになりにくく、**捨てるものの一覧が主役の選び方で
変わる**ので先に決めた。結果は **コンシューマ**。

### 生き返るもの

**ネタバレ抑止一式**（`reveal` / `spoilers=False` / [timeline.py](../glosspop/timeline.py) /
`first_scene_context()` / `context_up_to_first()`）。社内路線では丸ごと捨てるはず
だったが、物語や作品を扱うなら中心機能。**「渡すテキストそのもので担保する」という
約束も一緒に残る**（プロンプトの禁止文に頼らない）。

### 落ちるもの・形が変わるもの

- **点検（[doctor.py](../glosspop/doctor.py)）は落ちる。** 辞書を保守する人の道具で、
  コンシューマは自分から走らせない
- **統合（[merge.py](../glosspop/merge.py)）は画面ではなく警告になる。** 「同じ表記の
  ものがあります」を登録時に出す形。もともと「候補は同じ表記のものだけ」なので、
  出す場所を変えるだけで済む

### いちばん強い使い方: Web 小説

なろう・カクヨムを読みながら登場人物の相関図を作る。**案 4（Web 中心）・ネタバレ抑止・
キャラ相関図・[ego.js](../glosspop/static/ego.js) が同時に噛み合う**唯一の使い方。

[documents.py](../glosspop/documents.py) に**青空文庫の対応が既に入っている**
（Shift_JIS・ルビ・冒頭の説明ブロック）ので、青空文庫がそのまま隣接する市場になる。

### ストレージ: 案 2 は既定にできない

**個人に初回起動で OAuth を求めた時点で落ちる。** S3 は論外、Drive でも重い。

答えは案 3 が持っている。**個人辞書（端末保存・設定ゼロ）を既定にして、ストレージ
接続はグループ共有か控えを望んだときだけ**。順番が自然に決まる。

### iOS の消える挙動 —— **調べた。「タブなら消える / ホーム画面なら消えない」**

**7 日で消える規則は実在する。** ITP が「7 日間ユーザー操作の無いサイト」の
script-writable storage（IndexedDB・LocalStorage・SessionStorage・Service Worker
登録）を全部消す。**スクロールは操作に数えない**（クリック・タップ・キー入力のみ）。

**ホーム画面の Web アプリは明示的に除外されている。**

> The first-party domain of home screen web applications is exempt from ITP's
> 7-day cap on all script-writeable storage, i.e. ITP always skips that domain in
> its website data removal algorithm.

理由も書かれている —— ホーム画面の Web アプリは Safari の一部ではなく**独自の
使用日数カウンタを持つ**ため。データも Safari から隔離される。

**ただし「ITP 対象外」＝「絶対消えない」ではない。** 2023 年の保存ポリシー更新で
別の削除経路が入っている（容量超過・ストレージ逼迫・LRU）。既定の best-effort
モードは消されうる。

**そこで `navigator.storage.persist()`。** Safari 17 / iOS 17 から対応済みで、通れば
自動削除から保護される。許可の条件に**ホーム画面の Web アプリであることが名指しで
挙がっている**（WebKit: "grants a request based on heuristics like whether the
website is opened as a Home Screen Web App"）。ホーム画面に追加すると容量枠も
ブラウザ並みに上がる（origin 60% / 全体 80%。通常のアプリは 15% / 20%）。

**結論: 「まず PWA」は成立する。**

> **追記（辞書がサーバへ動いた結果）。** **この問題はほぼ消えた。** 辞書がサーバに
> あるなら、端末の storage が消えても**キャッシュが消えるだけ**。以下は「端末に
> 置くなら」の話として残す —— 端末保存へ戻す判断をしたときに読み直すため。

- ~~**個人辞書を端末だけに置くなら「ホーム画面に追加」が必須。**~~ タブで使っている
  人は 7 日で辞書が消える。iOS には install プロンプトが無く、共有 → ホーム画面に
  追加を手で踏ませるしかないので、**そこが最大の離脱点**になっていた。
  **サーバに置くことで、この離脱点が無くなった**
- **`persist()` の戻り値を見て、false なら画面に出す。** 推測しない。保護されて
  いないことを黙って進めない（打ち切りを黙らないのと同じ約束）。**辞書がサーバに
  あっても、読書位置や設定は端末側なので無意味にはならない**
- **容量は問題にならない。** 辞書は Markdown のテキストで、数千語でも数 MB。
  心配すべきは消えるかどうかだけ。**オフラインで epub を抱え込ませ始めたら別の話**

撤回した経緯がある。現在は動いているが、**この除外規定は Apple の裁量で動きうる。**

### AI の費用（→ 「課金」で答えを出した）

**ストレージを持たせても、これは肩代わりされない。**

コンシューマは辞書の本文を手で書かない（携帯ならなおさら）ので、AI 下書きは
**必須経路**になる。`claude -p` はサーバで人数ぶん起こせないので API 経路だけが残り、
その代金を誰が払うのかが残る。→ **BYOK と マネージドの二本立て**にした。

### 共有は 2 種類に割れる

コンシューマの「共有」は、**一緒に作る**より**見せる**のほうが主。

- **見せる**（作った相関図・辞書を公開リンクで見せる）—— 読み取り専用なので
  **多書き手の問題が一切発生しない**。安く、収集・装飾と直結する。**こちらを先に作る**
- **一緒に作る**（案 1 のグループ辞書）—— 書き込みの衝突が付いてくる

なお案 1 をやる場合、コンシューマのグループは 3〜5 人で書き込み頻度も低いので、
上に書いた「書けるのは持ち主だけ」は**緩められる** ——
エントリ単位の後勝ち + 控え で実用になるはず（あれは社内前提で書いた制約）。

## 使い方が割れる（＝全部移植しなくていい）

携帯で辞書の本文を手打ちするのは苦行だが、**AI 下書きがあると机より良いループ**に
なる（語をタップ → AI が書く → 承認）。いま「あると便利」な機能が、携帯では**中心**。

一方 [merge.js](../glosspop/static/merge.js) の統合・
[doctor.js](../glosspop/static/doctor.js) の点検・
[relations-draft.js](../glosspop/static/relations-draft.js) の関係の下書きは机の仕事。

**携帯 = 読む・引く・登録（AI 前提）／ 机 = 整える** で割れば、移植範囲はかなり小さい。

## 殻は PWA から

フロントが**依存ゼロの ES モジュールでビルド工程が無い**のがここで効く。5 つの HTML に
viewport meta は既に入っていて、`style.css` にも `max-width: 640px` / `760px` /
`560px` の分岐がある。**manifest と service worker を足すだけで installable になる。**
店で配りたくなったら Capacitor で包む、で後追いできる（iOS の PWA の扱いだけが読めない）。

RN / Flutter で native にすると、SVG 5 種と `placeLabels()` / `orderRows()` /
`arcSides()` の計算を全部書き直すことになる。**そこは触らない。**

## オンラインが主 —— 辞書はサーバに置く

**グループ機能はライブ性が要るので、オフラインは筋が悪い。** そこから引いて、
**グループに限らずオンラインを主とする。**

### 混ざりやすい 2 つの軸を分ける

- **どこにデータがあるか**（端末 / サーバ）
- **通信が無いときに動くと約束するか**（オフライン対応するか）

**後者は「約束しない」で確定。** 理由がもう 1 つあって、**Web 中心に決めた時点で
オフラインの価値はほぼ消えている** —— 読むもの自体が Web なので、通信が無ければ
そもそも読むものが無い。

### 前者が本当の分岐だった

| | 個人辞書 | 帰結 |
| --- | --- | --- |
| **(a) サーバ** | サーバ | **既存のパイプラインがそのまま残る** |
| (b) 端末 | 端末 | **照合を端末側でやる＝`linker.py` を JS へ移す** |

「ストレージが親」と書いた分岐と同じもの。**サーバが辞書を持たないと `Linker` に
全エントリを渡せない**ので、個人辞書を端末に置く限り照合は端末側に行く。

**(a) を採る。** 効果が大きい:

- **現行の一本道がそのまま残る** —— `render_source()` → `Linker.annotate()` →
  ブラウザ。Web 中心なら**サーバが取得して sanitize する経路が既にある**ので、
  注釈はその同じリクエストの中の 1 ステップ
- **「そのまま持っていける」リストが本当に Python のまま残る** —— linker・relations・
  resolve・graph・merge・timeline。**JS 移植と「2 か所に書かない」の心配ごと自体が消える**
- **iOS の 7 日問題が消える。** 辞書がサーバにあるなら端末の storage が消えても
  キャッシュが消えるだけ。**「ホーム画面に追加が必須」という最大の離脱点がなくなる**

### 代償と潰し方

**「設定ゼロ・アカウント不要」を失う。** 初回起動の壁として一度回避したものなので、
素直に戻さない。

**潰し方は匿名アカウント** —— 初回起動時に端末側で自動生成し、メールもパスワードも
聞かない。利用者から見た体験は「設定ゼロ」のまま、サーバから見ればアカウントがある。
あとからメールを結びつければ端末間で引き継げる、という段にすれば
**課金の階段に「引き継ぎ」という見返りが 1 段増える。**

**無料利用者ぶんのサーバ費用**も代償だが、辞書は Markdown のテキストで、照合も木に
してあるぶん実測 0.6ms。**容量も計算も軽い部類。** 重いのは AI だけで、そちらは
BYOK / マネージドで切ってある。

**プライバシーは現状と同じ。** URL 読み込みは今もサーバが取得しているので、新しく
外へ出るものは無い。

### 控えの位置づけは変わらない

サーバが正になっても**控えは利用者の手元に出せるまま**（zip 単位）。「引き継ぎも
保存先の移動も元を消さない」という既存の方針と揃う。

## 吹き出し —— 下からせり上がる形にする

**吹き出しがホバー前提**（[popup.js](../glosspop/static/popup.js) の `pointerover` /
`pointerout`）。携帯にホバーは無いのでタップになるが、**吹き出しの中の語を辿る
`drill()` もタップ**なので正面衝突する。

**答え: 浮かぶ吹き出しをやめ、下からせり上がって画面の何割かを残す形にする。**
いまの吹き出しが守っている 3 つの制約のうち、**2 つが構造的に消える。**

- **「位置の基準は元のアンカーのまま」が要らなくなる。** せり上がりにアンカーが
  無いので、「辿った先の語を基準にすると吹き出しが自分を追いかけて飛んでいく」
  という問題自体が存在しない
- **「ホバーでは開かない」も消える。** `inPop()` で 3 か所を弾いている理由が無くなる
- **残るのは「戻る道は `paint()` に 1 か所だけ」だけ。** むしろ重要度が上がる

**根本原因も消える。** いまの「両方消える」は、innerHTML を差し替えるとポインタが
指している要素ごと消え、**指す先を失った離脱で閉じる**のが正体だった。せり上がりは
離脱で閉じない（明示的に閉じる）ので差し替えても閉じない。**`pinned` が不要になる。**

### 切り分けは `place()` だけ

アンカーに依存しているのは `place()` 1 つで、`show()` から 3 回呼ばれているだけ。
`paint()` / `drill()` / `back()` / `trail` はどれも入れ物を知らない。**中身を描く道は
1 つのまま、入れ物だけ差し替える** —— `draw()` が 5 つの見せ方に `{ root, box }` を
返す形、`ai-style.js` が `host` だけ変えて共用する形と同じ型。

### せり上がり固有の、新しく守ること

- **押した語が残る側に来るようにスクロールする。** 「何割か残す」は、残った側に
  **その語がある**ときだけ意味がある。4 割せり上げた下に語が隠れたら、文脈が見えない
  点で元の吹き出しと同じ。**これが「位置の基準はアンカーのまま」の代わりに来る
  新しい不変条件**
- **閉じる手段を必ず持つ。** 携帯には `pointerout` が無いので現行の閉じ方が丸ごと
  効かない。スワイプダウン・背景タップ・戻るジェスチャの**どれか 1 つではなく全部**。
  閉じられない吹き出しは画面を占領する
- **戻るは OS のジェスチャに乗せる。** `trail` と `back()` が既に 1 か所にあるので
  繋ぐだけ
- **段は 2 つまで**（半分 / 全画面）。snap point が 3 つ以上あると操作が読めなくなる
- **分岐は `(hover: none) and (pointer: coarse)`。画面幅で切らないこと** ——
  狭くしたデスクトップの窓にはホバーがあるので、幅で切ると「マウスなのにせり上がる」

### ついでに良くなること

- **中身が長くても読める**（吹き出しは伸ばせない）
- **同名カテゴリ違いの複数件が並べやすい** —— `paint()` の 4 通りのうち「複数」が
  いちばん窮屈だった
- **語り手の顔を出す余地ができる**（複数辞書が並ぶとき行ごとに違う顔、という既存の
  設計が活きる）

### 気をつけること

- [select-add.js](../glosspop/static/select-add.js) の選択 →「＋ 辞書に登録」が
  **OS の選択メニューと場所を取り合う**
- [overlay.js](../glosspop/static/overlay.js) の上に出るので重なり順

## 課金

軸は 2 つ。**グループ機能**（人数と総量で毎月）と **LLM**（キーを用意できない人に
こちらのキーを使わせて毎月。知っている人は自分のキーで無料）。

### プロバイダは、2 つのモードで答えが違う

**ここを分けないと設計を誤る。** BYOK（利用者のキー）と マネージド（こちらのキー）は、
プロバイダを増やす代金がまったく違う。

**マネージドは 1 社に絞る。** 転売する以上、利用者ごとの計量・上限・不正利用対策・
原価計算が要り、**3 社に対応すると会計面が 3 倍になって利用者の得は 0**。キーを用意
できない人は「どの会社か」を気にしない、動けばいい。モデル毎の価格差を説明する羽目にも
なる。

**絞るなら Gemini。** 理由 3 つ、うち 1 つはこのリポジトリ自身が実測を持っている:

- **同じ仕事で Claude 258.6 秒 / Gemini 72.4 秒**（19 語・20 本要求。CLAUDE.md の実測）。
  所要時間は出力トークン数にほぼ比例するので、**これはほぼそのまま原価差**
- 単価が安く、**無料枠がある**ので「無料で始めて足りなくなったら課金」が作れる
- [llm.py](../glosspop/llm.py) に実装済み

**BYOK は 3 社 + 1。**

| 追加するもの | 得られるもの |
| --- | --- |
| Gemini / OpenAI / Anthropic | 名前で選ぶ人のほぼ全部 |
| **OpenAI 互換（`base_url` を書ける）** | OpenRouter・DeepSeek・Groq・xAI・Mistral・ローカルの Ollama / LM Studio が**アダプタ 1 つで全部** |

**4 つめがいちばん効く。** とくに **OpenRouter は「キーを 1 つ持てば数百モデル」**
なので、「知っていれば無料版を自分で使える」層の実際の答えはこれになりがち。

**用途が軽いのも効く。** この道具が LLM に頼むのは JSON を数千トークン返させるだけで、
上位モデルは要らない。安いモデルで成立する＝**マネージドの原価が読める**。

**モデルの一覧は焼き込まない**（API から引く）。CLAUDE.md の実例そのままで、記憶で
書くと知らない世代が漏れる。

### Claude Code CLI 経路は丸ごと死ぬ

サーバに CLI が無い。cwd を temp にする話・`--disallowed-tools` /
`--disable-slash-commands`・`_TRANSIENT_MARKS` の文言判定は**すべて不要**になる。
既定のプロバイダが変わるので、移植時の整理対象。

### 売り方はトークンではなく回数

**モデルごとの料金をコンシューマに出さない。** トークンが何かを知らない人に単価表を
見せると、そこで止まる。**「下書き ○ 回 / 月」で売って、内部でトークンを計量する。**

既にある部品に乗る —— 関係の下書きは**利用者に本数を選ばせて経過秒を出している**ので、
同じ場所に「この操作は ○ 回ぶん」と出せる。`llm.estimate_timeout()` の
`SECONDS_PER_ITEM` は実質すでに原価モデル。

**原価の上限も設計で担保できている。** 入力は `EXTRACT_TEXT_CHARS` と `sample_text()` で
間引くので**長編を読ませても入力は青天井にならない**、出力は割り当てで切れる。

### アカウントは課金したときだけ

課金にはログインが要るが、**「個人辞書は端末保存・設定ゼロ」と決めたばかり**。
**無料と BYOK は完全にアカウント不要、課金したときだけアカウント**にすれば両立する。
崩すと初回起動の壁が戻る。

### 控えを Drive へ出す

[archive.py](../glosspop/archive.py) の `export_bytes()` が既に zip を作り、**控えは
書き出しと同じ zip** という約束もあるので、出すもの自体は完成している。

**ただし Drive API を実装する前に、共有シートで済まないか試す。** 携帯の OS の
「ファイルに保存 / 共有」に zip を渡せば、利用者が iCloud でも Drive でも Dropbox でも
好きな場所に置ける。**OAuth も API キーも要らず、対応先が勝手に全部。**
定期的な自動控えを求められてから Drive API を足す。
