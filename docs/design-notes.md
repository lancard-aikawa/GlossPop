# 設計メモ

なぜそうなっているか。コードを読めば「何をしているか」は分かるが、「なぜ他の案を
採らなかったか」は残らないので、ここに書く。決まったことは消さずに積む。

## 辞書の保存形式: 1 用語 = 1 Markdown ファイル

**採用**: `data/glossary/<カテゴリ>/<slug>.md`（YAML frontmatter + 本文）

**理由**: 辞書は Claude にも人にも読ませたい。SQLite だと差分レビューも手編集も
できず、Claude に読ませるには変換が要る。Markdown なら本文がそのまま定義文になり、
`git diff` が意味のある単位で出る。数百件までは全ファイル読み込みで十分速い。

**捨てた案**:
- SQLite — 検索は速いが、手編集と差分レビューを失う代償が大きい
- 単一 JSON — 単純だが、複数箇所を同時に触ると競合しやすい

**代償**: 件数が数千を超えると `load_all()` が重くなる。そのときは mtime キャッシュ
（実装済み）だけでは足りないので索引を別に持つことになる。

## カテゴリ = ディレクトリ

**採用**: ディレクトリ名がカテゴリの正。frontmatter には書かない。

**理由**: 正が 2 箇所にあると必ずずれる。ファイラで見たときに分類が見えるのも利点。
`mkdir` しただけのディレクトリはマスターへ自動で取り込む。

**代償**: カテゴリ名がファイルシステムの制約を受ける。そのため
`models.normalize_category()` で全 OS の共通部分に絞り、NFC 正規化している
（macOS が NFD で返す濁点をそのままディレクトリ名にすると、Windows/Linux と
別物になる）。

**サブカテゴリはディレクトリにしていない**。2 段にすると移動と改名の組み合わせが
増える割に、得られるのは表示上のグルーピングだけで、それは frontmatter でも足りる。

## カテゴリマスターは辞書ごとに持つ

**採用**: 全体は `data/categories.yaml`、フォルダの辞書は
`<フォルダ>/.glosspop/categories.yaml`。並び順・説明・用語 0 件のカテゴリ・
サブカテゴリの先出しは、どちらでも同じように持てる。

**理由**: 当初はマスターをグローバルだけに置き、ローカルはディレクトリ名だけを正に
していた。**小説の「登場人物」が全体のマスターに残るのが邪魔**だったからで、その
判断自体は正しい。だが副作用として、フォルダ側は**並び順を決められなかった**
（名前順に固定され、主要人物 → 脇役 のように読みたい順に並べられない）。
マスターをフォルダの中に置けば、汚さずに並び順を持てる —— 元の懸念は
「マスターを 1 つしか持たない」ことに由来していて、複数持てば消える。

**波及**: `categories.py` の全関数が `scope` を取る。**キャッシュの鍵にファイルの
パス自体を入れる** —— 入れないとフォルダを切り替えても前のフォルダのマスターが
出てくる（`store._signature()` で踏んだのと同じ穴）。API・CLI・UI の 3 つとも
`scope` を渡すこと（渡さない経路が 1 つ残ると、フォルダのつもりの操作が全体に効く）。

**代償**: フォルダごとコピーすれば並び順も付いてくる代わりに、`.glosspop/` に
ファイルが 1 つ増える。**辞書が無いフォルダには作らない**（開いただけのフォルダを
汚さない）ので、ファイルができるのは実際にそのフォルダへ語を入れたときだけ。
書き出し / 取り込み (`archive.py`) に含めるのは従来どおり全体のぶんだけ ——
含めると、置き換えで消える範囲が広がる。

**並べ替えは全体を送る**（`PUT /api/category-order`）。「これを 1 つ上へ」という
差分を送る形にすると、続けて押したときに後の書き込みが前のものを消す
（関係の書き込みを 1 本ずつ PUT しないのと同じ理由）。送られなかったカテゴリは
後ろに残す —— 落とすと、一覧を作ってから送るまでの間に増えたものが黙って消える。

## 一意キーは「カテゴリ + 用語」

**採用**: 同じ用語名でもカテゴリが違えば別エントリ。衝突判定は同一カテゴリ内だけ。

**理由**: 「ソース」がプログラミングにも料理にもある、という状況が実際に起きる。
用語名だけを一意キーにすると、片方を登録できないか、名前を歪めることになる。

**波及**: `find_by_surface()` がリストを返す。自動リンクは「表記」を `data-gloss` に
持たせ、吹き出し側が表記から全件を引く。リンク先は 1 件なら詳細ページ、複数なら
一覧検索。

## 同名が複数あるときの吹き出し: アコーディオン

**採用**: カテゴリごとの `<details>`。先頭だけ開く。1 件のときは従来どおりの見た目。

**捨てた案**:
- ヘッダにタブを並べる — 幅 360px の吹き出しでは、カテゴリ名が長い / 件数が多いと
  あふれる
- 全部を縦に展開 — クリック不要だが、本文が長いと吹き出しが壁になる
- 2 段階（一覧 → 選んで詳細） — 小さく収まるが、1 件目を読むのにも 1 クリック要る

`<details>` はネイティブでキーボード操作とスクリーンリーダーに対応するので、
自前のタブ実装より安い。

## AI 連携: Claude Code CLI をサブプロセス起動

**採用**: `claude -p` を `subprocess.run()` で叩く。

**理由**: API キーを別途用意させたくない。Claude Code の認証をそのまま流用できる。

**代償**: 1 回 10〜30 秒かかり、並列性も低い。UI は「数十秒かかります」と明示して
待たせる作りにしてある。

**踏んだ罠**: プロジェクト内で実行すると CLAUDE.md と `gloss-add` スキルを読み込み、
「重複確認のため CLI を実行させてほしい」と要求して承認待ちで固まる（非対話なので
永久に返らない）。プロジェクト外の cwd で、全ツールを禁止して呼ぶ必要がある。
詳細は [CLAUDE.md](../CLAUDE.md)。

## 自動リンクの照合単位: 「読者に見えるテキスト」

**採用**: HTML を走査してインライン要素をまたいだテキストを組み立て、そこで照合する。
一致がノードをまたぐ場合は断片ごとに `<a>` を張り、CSS で下線を繋げる。

**理由**: 最初はテキストノード単位で照合していたが、`**冪**等` のように装飾が語を
分断していると一致しなかった。読者には「冪等」に見えているのにリンクされないのは
バグにしか見えない。

**境界**: ブロック要素と `<br>` はまたがない。またぐと `<p>冪</p><p>等</p>` が
偶然一致してしまう。

**捨てた案**: クライアント側で DOM を走査して置換する。サーバ側でやるほうが
テストしやすく、辞書ページとビューアで実装を共有できる。

## インラインコードはリンク対象、コードブロックは対象外

**採用**: `` `用語` `` はリンクする。``` ``` ``` フェンスと `<pre>` はしない。

**理由**: 日本語の技術文書ではバッククォートを「コード」ではなく用語の強調として
使うことが多い。README 内の `` `機械学習` `` がリンクされないのは期待外れになる。
実際のコードを載せるのはコードブロックのほうなので、そこで線を引ける。

**代償**: コード片の中の識別子が拾われることがある。実例として、別名 `MD` が
`.md` という拡張子に当たった（→ 次の節）。

## 短い大文字略語だけ大文字小文字を区別する

**採用**: 3 文字以下の全大文字 ASCII 表記（`MD` `ML` `DB`）は大文字小文字を区別して
照合する。それ以外は従来どおり区別しない（`linker._case_sensitive()`）。

**理由**: 「Markdown」の別名 `MD` が `README.md` の拡張子に当たり、README を開くと
5 箇所がリンクになった。境界チェックは「英数字以外なら通す」ので `.` が境界として
通る。インラインコードをリンク対象に加えたことで表面化した（コード片には拡張子や
オプション名が多い）。**略語は本文でも大文字で書かれる**ので、ここだけ区別すれば
実害なく潰せる。

**捨てた案**:

- **辞書側で対処**（`MD` を別名から外す）— コードは変わらないが、`ML` `DB` を
  登録するたびに人が同じ判断をすることになる。仕組みで防げない
- **拡張子ガード**（直前が `.` の ASCII 表記を無視）— 狙いは正確に潰せるが、
  `` `md` `` 単体や `docs/md/` のようなパス片には当たったまま残る。規則としても
  場当たり的で、次に似た形が出たときに足す先が無い

**代償**: `API` を `api` と小文字で書いた箇所はリンクされなくなる。日本語の技術文書で
略語を小文字で書くのは、たいていコード中の識別子（＝リンクしたくない場所）なので
許容した。

**残っている穴**: 上限が 3 文字なので `HTML` は対象外で、`.html` には当たったまま。
広げるなら `_ACRONYM_MAX_LEN` だけを変える。上限を外すと `NASA` のような全大文字の
固有名詞まで区別することになるので、実際に困ってから広げる。

## CLI のローカル辞書は `--folder` で指す

**採用**: `glosspop add --scope local --folder <DIR>`。`--folder` は
`config.set_content_dir()` を呼ぶだけで、そこから先はサーバとまったく同じ経路
（`store.glossary_dir(LOCAL_SCOPE)` → 祖先方向に `.glosspop` を探す）を通る。

**理由**: ローカル辞書は「開いているフォルダ」から決まるが、一度きりの CLI には
その状態が無い。CLI 用に辞書を探す実装を別に書くと、祖先方向の探索・段数の上限・
URL 辞書との排他といった規則が 2 つに分かれ、必ずずれる。**状態を先に決めてから
既存の経路に流す**ほうが、覚えることが増えない。

**捨てた案**: `--local-dir` で `.glosspop` を直接指す。祖先方向の探索を迂回するので
「1 巻 2 巻で作品フォルダの辞書を共有する」規則が CLI からだけ効かなくなる。

**代償**: `--folder` を省いて `--scope local` を指定すると、既定の content フォルダの
辞書に書かれる。**書いた場所を必ず stderr に出す**ことで黙らせない（ビューアが
親の辞書を使っているときに場所を画面へ出しているのと同じ理由）。

## 辞書本文は保存時に 1 文 1 行へ整形

**採用**: 60 字を超える行を句点で割って保存し、表示側は単一改行を `<br>` にする。

**理由**: AI は 1 段落に 5〜6 文を詰め込みがちで、そのまま出すと読みづらい壁になる。
保存時に整形すると、ファイル自体が読みやすくなり `git diff` も文単位になる。

**触らないもの**: ビューアで開くソース文書。ユーザーの `.md` を勝手に整形しない。
そのため markdown インスタンスを 2 つ持っている（`breaks` の有無）。

## 読書位置は段落の番号で覚える

**採用**: 文書ごとに「画面の上端にある段落の番号」を localStorage に持ち、開き直したら
そこへ寄せる（`progress.js`）。戻したことは画面に出し、「先頭から読む」を添える。

**理由**: px で持つと、窓の幅・文字サイズ・表示オプションを変えただけで別の場所に
なる。段落の並びはそれらで動かない。読み上げが段落単位なのとも揃う。

**覚えないもの**: 「ファイルを開く」「ドロップ」「貼り付け」で開いた文書。ブラウザが
絶対パスを渡さないので、ファイル名しか手掛かりが無い。**無いものに名前を付けて覚えると、
同名の別ファイルを同じ鍵で上書きする**。文書内リンクを辿れないのと同じ制約。

**捨てた案**:

- **黙って戻す** — どこから読み始めたのか分からないまま途中の画面が出る。この
  リポジトリはずっと「黙って別のことをしない」で通してきたので、案内を出す側に倒した
- **「続きから読む」を押させる** — 押さない限り先頭のままなので、開くたびに
  スクロールし直すことになる。長い本ほど手間が増える

**代償**: 段落の並びが変わる編集（章の入れ替え）をすると、覚えている位置がずれる。
文書の同一性まで見る（内容のハッシュ等）と、少し直しただけで全部忘れることになるので
取らなかった。

## タグにマスターを作らない

**採用**: `/api/tags` が**使われているタグを数え上げて**返す。絞り込みは 1 つだけ選ぶ。

**理由**: カテゴリはディレクトリという実体があるからマスター (`categories.yaml`) を
持てるが、タグには置き場所が無い。マスターを作ると用語 0 件のタグが残り、掃除する
口が要る。数え上げなら、最後の 1 語から外した時点で選択肢からも消える。

**捨てた案**: 複数タグの AND / OR。どちらにするかを決めることになり、カテゴリの
絞り込みとも見た目が揃わない。必要になってから広げる。

**直したもの**: 用語ページの `#タグ` は `/glossary?q=<タグ名>` に飛んでいたので、
**そのタグ名が本文に出るだけの語**まで混ざっていた。いまは `?tag=` で完全一致。

## 横断検索は索引を持たない

**採用**: `/api/content-search` が開いているフォルダの文書をその場で読んで探す。

**理由**: 索引を持つと、外のエディタで書き換えられたファイルとずれる。辞書側は
mtime で読み直して解決しているが、本文は量が桁違いなので同じ手が使えない。
`MAX_CONTENT_FILES` で一覧の件数が既に頭打ちなので、その場読みで足りる。

**打ち切りは必ず返す**（`files_truncated` / `hits_truncated` / `skipped`）。黙って
切ると「この語は無かった」と区別が付かない —— 一覧の `truncated` と同じ考え方。

**ヒットへ寄せる方法が初出ジャンプと違う**。`?term=` は登録済みの語なので
`[data-gloss]` を探せるが、検索語は辞書に無いことのほうが多い。見えているテキストで
段落を探して光らせている。

## 相関図の辺はダイアログで直す

**採用**: 辺を押すと `dialog.sheet` が開き、その関係の 5 項目を直せる（削除もここ）。

**理由**: 点検ページを「その場で直す」にしたのと同じで、関係を 1 本直すために辞書
ページへ移動させると、図を見ながらの手直しが続かない。ダイアログはカテゴリ管理・
登録・抽出でも使っている作法なので、新しい見た目を増やさずに済む。

**捨てた案**:

- **図の脇に常設パネル** — 図を見ながら何本も直せるが、`graph.html` を 2 列に
  変えることになり、狭い画面で図が潰れる。得るものに対して構造の変更が大きい
- **辞書ページの関係欄へ飛ばす** — サーバもクライアントも変えずに済むが、
  ページを渡り歩かせないという動機そのものを満たさない

**辺から書き手へたどる鍵**は「エントリの何番目の関係か」(`index`) と
「書かれたままの行き先」(`rel_to`)。`to` は解決後の ref なので、ファイルに書いて
ある文字列とは違いうる（用語名だけで書ける仕様の裏返し）。

**番号は伏せた関係も数える。** 出した辺だけを数えると、判明位置つきを伏せたぶんだけ
ずれて**別の関係を書き換える**。黙って壊れる形なので、テストで見張っている。

**書く直前に読み直して行き先を照合する。** 番号は図を描いた時点のものなので、
その間に関係が増減していると別の関係を指す。合わなければ書かずに読み込み直させる。

## 辞書の取り込みは「置き換え」と「併合」。どちらも消す前に控えを取る

**採用**: 取り込み方を 2 つ持つ（`archive.py`）。`replace` は zip の中身で丸ごと
入れ替える。`merge` は zip にしか無い語を足し、**両方にあるものは取り込む側で
上書き**する（手元にしか無い語は残る）。実行の前に、いまの辞書を同じ形式の zip で
`data/backups/` に書き出す。

**併合の衝突は「取り込む側が勝つ」の 1 行だけ**。決め方はこれしか無かった:

- `updated_at` の新しいほう —— **時計がずれた PC が 1 台あると静かに古いほうが
  勝つ**。しかも勝ったほうが正だと思い込んだまま気付かない
- 1 件ずつ選ばせる —— 統合（下記）では成立するが、**100 語が衝突する併合では
  人が捌けない**。捌けないものを出すと、結局まとめて「はい」を押される
- いまある側が勝つ —— 安全だが、**更新を持ち込むという用途そのものが消える**

規則を 1 つに絞る代わりに、**控えを必ず取り、上書きした語を全部名前で返す**。
消えたものを控えから拾い直せるなら、単純な規則で足りる。**黙って消える箇所を
ゼロにする**のが、選ばせないことの引き換え。

**実行の前に件数を出す**（`plan()`）。「入れ替わります」の一言だけで押させると、
何語が消えるのか分からないまま実行することになる。下見は数えるだけで控えも取らない。

**併合でも入れ替えはディレクトリごと**。いまの辞書を作業用ディレクトリに複製して
から zip の内容を上書きし、rename 2 回で入れ替える。1 ファイルずつ書く形にすると、
途中で失敗したときに**半分だけ新しい辞書**が残る。

**渡す範囲は書き出す側だけで決める**（`export_bytes(only=…)`）。1 カテゴリだけ渡す
道が無かったが、**取り込む側は 1 行も変えていない** —— 併合はもともと「入っている
ものを足して上書きする」だけなので、中身が一部でもそのまま通る。取り込み側に
「一部を取り込むモード」を足すと、置き換え・併合との組み合わせが増えて、どれを
選べばよいのかが人に分からなくなる。

- **一部のときはカテゴリマスターも選んだぶんだけ**組み立て直す（渡す相手に関係の
  無いカテゴリの説明と並びを送りつけない）。**全部書き出すときはファイルそのまま**
  —— 控え (`write_backup`) もここを通るので、書式ごと元に戻せる形を崩さない
- **一部であることは zip の中にも残す**（manifest の `partial` / `categories`）。
  受け取った側が「これで全部」と思わないように
- **行き先が外に出る関係を先に数える**（`export_plan()`）。関係は名前で書くので、
  相手が入っていない zip を渡すと**保存はできるがリンクにも図の辺にもならない**。
  実行の前に件数を出す、という取り込み側の約束と同じ扱いにした。数えるのは
  解決できている関係だけ —— もともと壊れている参照は点検の担当で、二重に出さない
- **カテゴリ名はファイル名に入れない**（`-part-` とだけ書く）。空白も日本語も
  使えるので、`Content-Disposition` に載せると経路ごとに化ける

**控えは中を見られて、1 件だけ戻せる**（`list_backups` / `backup_contents` /
`restore_entry`）。併合の衝突を「取り込む側が勝つ」の 1 行に決めた引き換えは
「控えを必ず取る」ことだったが、**戻すのに zip を手で開かせるのでは約束が半分**
しか果たせていなかった。守っていること:

- **控えの名前は外へ出さない。** 画面から来る文字列なので、`..` や絶対パスを
  そのまま繋がず、組み立てた結果が控えの置き場所の中にあることを最後に確かめる
  （外から来た書庫をライブラリ任せにしない、と同じ規則）
- **戻すときは保存し直さない。** 控えは「消える前の写し」なので、ファイルの中身を
  そのまま書く。`store.save()` を通すと本文の整形や `updated_at` が変わり、
  **書いてあったとおりに戻る**という性質が消える
- **上書きになるかを押す前に出す**（`here`）。1 件ずつ戻す経路では控えを取らない
  ので、代わりに先に見せる（削除・統合と同じ扱い）
- **古いものを自動で消す口は作らない。** 溜まるのは事実だが、控えは消える前の
  唯一の写しなので、勝手に捨てると約束のほうが壊れる。合計の大きさを出して人に
  決めさせる
- **並べ替えはファイル名から作った鍵で**（`_backup_order`）。名前をそのまま
  並べると、同じ秒に 2 回取ったときの `-2` が `.` より小さくて**古いほうが先に
  来る**。ファイルの時刻で並べるのも駄目 —— Windows の時計は 15ms ほどの粒度で、
  続けて取った 2 つが同じ時刻になりうる（そこで競走するテストは書かない）

**カテゴリマスターは併合では手元の並びを保つ**。丸ごと差し替えると、手元にしか
無いカテゴリが順序と説明だけ失う（ディレクトリは残るので次の `load()` で名前順に
復活し、**決めた並びが黙って崩れる**）。衝突の扱いはエントリと同じで取り込む側が
勝つが、**サブカテゴリだけは和集合**にする —— あれは値ではなく「先出しの候補」
なので、消して得るものが無い。

**控えを自動にした理由**: これは辞書を丸ごと消しうる**唯一の操作**。
`copy_data_root` も `move` も `installer` も「元を消さない」で通してきたので、
ここだけ「先にバックアップしてください」と注意書きにすると必ず抜ける。控えは
書き出しとまったく同じ zip なので、**そのまま取り込み直せば戻る**（テストで見張る）。

**入れ替えはディレクトリごと**（2 回の rename）。1 ファイルずつ消して書くと、途中で
失敗したときに**半分だけ新しい辞書**が残る。どちらの版でもない状態がいちばん困る。

**含めるのは全体の辞書とカテゴリマスターだけ**。フォルダの辞書 (`.glosspop`) は
フォルダごとコピーすれば運べるし、URL ごとの辞書は URL に紐づく。含めないぶん、
**取り込みで変わる範囲が辞書 1 か所に収まる**。

**中身は Markdown のまま**入れる。独自形式にすると、解凍しても読めない＝アプリが
無いと救い出せなくなる。1 用語 = 1 Markdown にした理由がそのまま効く。

## 一覧のカードは `<a>` にしない（選択と両立しないため）

**採用**: 辞書一覧のカードは `<div>`。**見出しだけが本物のリンク**で、それ以外の
ところはクリックのハンドラで飛ばす（`glossary.js` の `card()`）。

**理由**: カード全体を `<a>` にすると、**リンクの中ではドラッグが「リンクを掴む」
になって文字を選べない**。一覧にだけ「選択 → 辞書に登録」の口が無かったのはこれが
理由で、`draggable="false"` を付けても Chrome は選択させてくれなかった（実際に
試して確かめた）。要約に出てきた知らない語をその場で登録できるほうが、
一覧の使い道に合う。

**得たもの**: 見出しの中クリック・Ctrl クリック（別タブ）は本物のリンクなので
そのまま効く。キーボードの Tab も見出しに止まる。カード全体が 1 つの巨大な
リンクだったころより、読み上げの単位としてもまとも。

**代償**: 見出し以外のところでは中クリックが効かない（ただのクリック判定なので）。
カードが `<a>` でなくなったぶん `cursor: pointer` を自分で当てている。
**「飛べること」はテストで見張る** —— リンクを外した以上、壊れても HTML は
それらしく見えるので、画面を開くまで気付けない。

## 本文は索引を持たず、解釈済みのものを使い回す

**採用**: 横断検索は毎回すべてのファイルを見る。ただし**変わっていないファイルは
読み直さない**（`documents.read_cached()`。鍵はパス + mtime + サイズ）。

**理由**: 測ると、重いのは**epub の解釈**だった（1 冊 9.6 ms。`.md` は 0.1 ms。
epub 10 冊 + `.md` 40 件のフォルダで、検索 1 回のうち 95% が epub）。読み込み
そのものではないので、**索引を作らなくても解釈を使い回すだけで大半が消える**。

もうひとつ、測るまで見えていなかったこと: **検索の重さは語によって違う。**
よく出る語は `MAX_SEARCH_HITS` ですぐ打ち切られるので 0.5 ms しかかからない。
全部読むのは**見つからない語を探したとき**だけで、そこが 108 ms だった。

| | 前 | 後 |
| --- | ---: | ---: |
| 見つからない語で検索（初回） | 108.6 ms | 108.6 ms |
| 同上（2 回目以降） | 108.6 ms | 11.8 ms |
| まとめ登録の初出探し 20 語ぶん | 177.8 ms | 17.0 ms |

**索引を作らないのは、索引がずれると嘘をつくから。** 辞書のキャッシュは
「読み直せば正しい」で済むが、検索の索引は取りこぼしが**「その語は無かった」と
区別が付かない**（打ち切りを必ず返しているのと同じ理由）。いまの形は毎回すべての
ファイルを見るので、取りこぼしようがない。

**代償**: 解釈済みの本文をメモリに抱える。**数と総文字数の両方で上限を持つ**
（`CACHE_MAX_FILES` / `CACHE_MAX_CHARS`）—— 数だけだと長編ばかりのフォルダで
数百 MB を抱えうるし、文字数だけだと小さいファイルが際限なく増える。
返す `Document` は使い回されるので、呼び出し側で書き換えないこと。

## 自動リンクの照合は表記を木にまとめる（測ってから決めた）

**採用**: `Linker` の正規表現は、表記を `a|ab|abc` と並べるのではなく**前方一致で
木にまとめる**（`linker._trie`）。組み立てた `Linker` は辞書が変わるまで使い回し
（`app._linker()`）、`store._signature()` は `os.scandir` で作る。

**測ってから決めた。** 手を付ける前の想定は「`Linker` の組み立てが効く」だったが、
実測すると内訳が違った（3000 語・本文 2120 字。1 リクエストぶん）:

| | 前 | 後 |
| --- | ---: | ---: |
| `_signature()`（変更の検出） | 33.6 ms | 5.7 ms |
| `Linker()` の組み立て | 20.2 ms | 32.1 ms（使い回すので 1 回だけ） |
| `annotate()`（照合） | 112.0 ms | 0.6 ms |
| **1 リクエスト** | **165.7 ms** | **6.4 ms** |

**効いていたのは照合（68%）で、組み立ては 12% しかなかった。** 素直に並べた
正規表現は候補ごとに順に試すので、**本文の長さ × 候補数**で伸びる。木にまとめると
候補数の効きが消える（語数を 30 倍にしても照合は 1.7 倍にしかならない）。

**組み立ては少し遅くなった**（20 → 32 ms）。木を組む Python の仕事が増えるぶんで、
使い回す前提なら払う価値がある。ここは「速くなったと思ったら、同じ仕事量を
比べているか先に疑う」の逆で、**遅くなったほうを受け入れる判断**。

**`_signature()` は `os.scandir` にした。** ディレクトリを読んだ時点で OS は各項目の
情報を返しているので、`scandir` の `stat()` は追加のシステムコールを出さない。
`Path.glob` + `path.stat()` は項目ごとに呼び直すぶん件数に比例する。**意味は
まったく変えていない**（同じ値を作る）ので、これは純粋に速いだけの変更。

**代償と担保**: 木にまとめる変換は、間違えると**速いのに結果が違う**という
いちばん質の悪い壊れ方をする。テストに**素直に並べた版との突き合わせ**を置いて
あり（`test_linker.py` の `_flat`）、前方一致・大文字小文字・境界チェックの
組み合わせで同じ位置に同じ長さで当たることを確かめている。使い回しのほうは
「外のエディタで足したファイルを拾う」をテストで見張っている —— 鍵を時間や
件数に変えると、そこが黙って壊れる。

## 統合は「手で選ぶ」だけ。似ているものを機械で挙げない

**採用**: 割れてしまった同じものは、人が 2 つ選んだときだけまとめる
（`merge.py` / 用語ページの「まとめる」）。点検にも一覧にも「同じ人物かも
しれません」は出さない。

**理由**: **カテゴリ違いの同名はこの辞書の狙いどおりの機能**（「ソース」が
プログラミングにも料理にもある）。似ているものを機械で挙げると、正常なものを
大量に警告することになり、点検の「正常なものを問題として出さない」という約束が
崩れる。崩れた瞬間に本物の壊れが埋もれる。候補として先に出すのは**同じ表記の
もの**だけで、あとは検索してもらう。

**消える側の用語名は残す側の別名に回す**。ここを落とすと、本文でその表記が
リンクにならず、名前で書かれた他エントリの関係も行き先を失う（関係に ID は
無く、名前で書けるのがこの辞書の仕様）。「まとめたのに片方の呼び方だけ
引けない」のでは意味がない。

**参照側のファイルは書き換えない**。消える側の ref は `former_refs` に積むので、
ref で書かれた関係は転送で解決し続ける（カテゴリ移動と同じ wiki のリダイレクト）。
全エントリを書き換えて回る実装にすると、手で `mv` された経路が必ず漏れる。

**代償**: 畳めない項目（本文・要約・同じ相手への関係）は人が決めるので、
一発では終わらない。下見 (`GET /api/merge`) と実行 (`POST /api/merge`) を
分けてあるのはそのため。**サーバは黙って片方に寄せない** —— 寄せた瞬間に、
選ばなかったほうが確認の機会も無く消える。この作りは 1 組 2 件だから成立する
のであって、**辞書の併合（100 語が衝突しうる）には流用できない**。

## 目次はアンカーを埋めずに作る

**採用**: `/api/content/{rel}` が章 / ページの名前だけを返し、ビューアが描き終わった
本文を頭から 1 回なぞって段落の番号に対応づける（`locateSections`）。

**理由**: 章の見出しは `documents.py` がすでに本文へ入れている（epub は元の見出し、
無ければ `第 N 章`。pdf は `【p.42】`）。改めてアンカーを埋めるなら、`htmlclean` が
`id` を落としているところに例外を作ることになり、**外から来た HTML の id が
アプリの id と衝突する**余地が生まれる（`#doc` を持つ epub があれば
`getElementById` が壊れる）。

**捨てた案**:

- **`id` を残すようサニタイザを緩める** — 上記の衝突。接頭辞で逃げる手もあるが、
  「許可制で未知のものは必ず落ちる」という性質を弱める
- **`/api/render` に節の位置を返させる** — 描画とテキストの対応をサーバ側で持つ
  ことになり、表示オプション（最初の 1 回だけリンク）で崩れる

**前の節より後ろだけを探す。** 章の名前は本文にも出てくるので、文書全体から最初の
一致を採ると手前へ飛ぶ。節が文書順に並ぶ性質でこれを避けている。
対応づけられなかった数は画面に出す（黙って欠けた目次を出さない）。

## 用語の出現は自動リンクと同じ規則で探す

**採用**: `/api/content-search?ref=` は `Linker` の正規表現を素のテキストに当てる
（`Linker.finditer()`）。

**理由**: 素の部分一致にすると `API` が `rapid` に当たる。「本文でリンクになる語」と
「出てくる文書」がずれると、**リンクにならない語を「出てくる」と言う**ことになる。
規則を 2 か所に書かないための口を Linker 側に開けた。

**使用例に貼る文は文の切れ目まで採る**（`_sentence`）。抜粋は文字数で切るので
前後が欠け、「…」つきの半端な文が辞書に溜まる。辞書に残るものと、画面で読み流す
ものとで、切り方を分けている。

## 外部 HTML は許可制でサニタイズ

**採用**: 標準ライブラリの `HTMLParser` で、残すタグ・属性を列挙する方式。

**理由**: 依存を増やしたくない。許可制なら未知のタグ・属性は必ず落ちる。
`<main>`/`<article>` を優先して本文だけ採るので、ナビゲーションや広告が混ざらない。

**代償**: 完璧なサニタイザではない。JavaScript で描画するページは本文が取れない
（その旨をエラーメッセージに書いてある）。ローカル専用ツールなので localhost や
社内ホストも意図的に許可している。

## 宿題の見直しは「タグを打つ直前」に寄せる

**採用**: `docs/open-questions.md` を見直すきっかけを 2 つ置く。

- CLAUDE.md の「変更時に一緒に直すもの」に行を足す（機能を足したら見直す）
- `check.cmd ci` の最後に、**残っている宿題の見出しを読み上げる**。前回のタグ以降に
  コミットがあるのにこの file を一度も触っていなければ、あわせて警告する

**理由**: 一度、機能が 5 つ入る間この file が一度も更新されず、**解決済みの項目が
残ったまま**になった。残っていると「まだ無いもの」に見えるので、次に読む人が
同じ検討をやり直す。害が出るのは主に**リリースのとき**（何が入って何が残っているかを
一覧する場面）なので、そこを関門にした。`check.cmd ci` はタグの前に必ず通る。

**落とさず警告にした理由**: 「file を触った」は「見直した」の証明にならない。
落とす作りにすると、中身を見ずに空白を足して通す動機が生まれる。バージョンの
上げ忘れと同じ扱い（黄色で出して、判断は人に残す）。

**代償**: 見直しを強制はできない。強制するなら、宿題 1 件ごとに「解決したことを
機械で確かめられる条件」を書かせることになるが、**それが書ける宿題は、そもそも
宿題ではなくテストにできる**。書けないものが残るのがこの file なので、そこは
人の目に返す。

## 関係の下書きは、読むものが決まっている場所にだけ置く

**採用**: 相関図から「✨ 関係を下書き」を外し、**ビューアの本文の右上**へ単独の
ボタンとして置く（表示中の文書を渡す）。抽出ダイアログの中の「✨ 続けて関係を探す」
はそのまま残す。

**理由**: 相関図は `store.load_all()` をそのまま出す**辞書全体の図**なのに、
下書きは**開いているフォルダの全文書**を読んでいた（`_read_content_docs`。URL を
読んでいてもフォルダを読む）。同じツールバーに並んでいるので「図に出ている語に
ついて探す」と読めるが、実際に読む範囲は図とも、ビューアで開いているものとも
一致しない。**押した人の期待と、実際に読むものが食い違うボタン**だった。

もう一つは道の問題で、表示中の文書から下書きできる経路が抽出ダイアログの**中**に
しか無かった（候補を抽出 → 下書き → 保存し終えた行があるときだけ出る）。
閉じれば消えるので、**読むたびに抽出と登録を通し直す**ことになっていた。

**捨てた案**:

- **相関図に残したまま文言で説明する** — 「開いているフォルダを読みます」と
  添えるだけなら安いが、**読む範囲が図と違うことは変わらない**。注意書きで
  食い違いを埋めるのは、この辞書でずっと避けてきたやり方（黙って欠けた図を
  出さない、打ち切りを必ず返す、と同じ筋）
- **相関図の下書きを「図に出ている語だけ」に絞る** — 対象語はもともと
  `_relation_scope` で絞れているので、揃っていないのは**読む本文**のほう。
  図の側に「どの文書か」が無い以上、ここだけ揃えようがない

**代償**: フォルダ全体から関係を引く道は、**フォルダから用語を抽出**の続きだけに
なった（そこは「フォルダが対象」と分かって押す場所なので食い違わない）。
図と辞書の範囲をどう決めるかは片付いていない（→ [open-questions.md](open-questions.md) の 7 番）。

## 相関図は 2 つの範囲を持つ（辞書全体 / この文書だけ）。どちらかは必ず画面に書く

**採用**: `/api/graph?doc=<content の中のパス>` で、**その文書に出てくる語だけ**の
図を出せるようにした。入り口はビューアの **🕸 この文書の相関図**。既定（`doc` 無し）は
これまでどおり辞書全体で、**どちらを出しているかを常にツールバーに書く**。

**理由**: 相関図は `store.load_all()` を出すだけで、読んでいるものと繋がっていなかった。
一方で「関係を下書き」は本文を読む。片方だけ文書に結びついているので、下書きした関係が
図のどこに増えたのか分からず、**「中途半端で矛盾した設定」**になっていた。下書きを
本文の側へ動かした（上記）だけでは、図が全体のままなので食い違いは残る。

**「出てくる」の判定は `Linker` から出す**（`entries_in()`）。素の部分一致にすると
`API` が `rapid` に当たり、**本文でリンクにならない語を図に出す**ことになる。
出現探し (`?ref=`) と同じ理由で、規則は 1 か所から出す。

**相手が出てこない関係は落とす**（数だけ `outside` で返す）。カテゴリ絞りは辺が
宙に浮かないよう相手を `outside` ノードとして足すが、**同じことをここでやると、その
文書に出てこない語が図に混ざる** —— それは絞る前の状態そのもので、直したかった食い違いに
戻る。未登録の相手（赤リンク）も同じ扱い。辞書に無い語は文書に出てくる語ではありえない。

**捨てた案**:

- **1 ホップ先まで出す** — 関係が切れずに済むが、「この文書の図」と言えなくなる。
  出すなら別の名前の機能（「この語のまわり」）にすべきで、絞り込みの既定にはできない
- **クライアントが `?ref=` を並べて渡す** — サーバがファイルを読まずに済むが、
  語数ぶん URL が伸びる。**貼り付けたテキストにも効く**という利点はあるので、
  必要になったらこちら（いまは `doc` の無い経路ではリンクを出さない）
- **フォルダ全体に広げる** — 「開いているフォルダの図」は下書きの旧仕様と同じ範囲だが、
  読むファイル数ぶん重くなり、**横断検索と同じ打ち切りの話**を図にも持ち込むことになる

**代償**: 貼り付け・ドロップ・URL では絞れない（`?doc=` はサーバが content の中を
読み直す仕組みのため）。ビューア側でリンクを出さないことで、押せるのに絞れない状態は
作っていない。

## 辞書・相関図・点検はビューアに重ねる（ページとして開き直さない）

**採用**: ビューアを下層に置いたまま、辞書一覧・用語ページ・相関図・点検を
**覆い（`overlay.js`）として上に重ねる**。URL は `history.pushState` で合わせ、
ブラウザの「戻る」でも閉じる。`/glossary` などのページも**残してある**（直接
開かれた URL・ブックマーク・別窓のため）。中身の出どころは 1 つで、各モジュールの
`mount(host, …)` をページと覆いの両方から呼ぶ。

**理由**: 測ったから。相関図からビューアへ戻るのに **149 ms**（銀河鉄道の夜・
39,203 字。n=5 の中央値）かかっていた。内訳はサーバの render が 18 ms、
ブラウザの描画が 22 ms、残りがページの作り直し。**本文が長いほど伸びる** ——
render だけで 157K 字 = 72 ms、353K 字（『吾輩は猫である』級）= 159 ms、
これに 1.7 MB の HTML を描く時間が乗るので、長編では往復 0.5 秒級になる。
重ねれば**閉じるのは 5 ms**（実測）で、読書位置・スクロール・読み上げの状態も
そのまま残る。

**捨てた案**:

- **ブラウザの「戻る」に任せる（bfcache）** — 何も作らずに済むが、**効いていない**。
  `pageshow` の `persisted` が立たず、ページは作り直されていた（132 ms）。
  効く効かないがブラウザ任せなうえ、確かめる手段が「実測」しかないものに
  往復の速さを預けられない
- **描画済みの本文を `sessionStorage` に持って戻ったときに貼る** — ページ構成を
  変えずに済むが、**長編ほど効かない**（1.7 MB の HTML を保存して読み出して
  貼り直すのは、作り直すのと大差ない）。読書位置・読み上げの状態も戻らない
- **`iframe` に各ページを出す** — モジュールを 1 行も直さずに済むが、
  **層をまたぐ操作が全部 `postMessage` 越し**になる。重ねる目的の半分は
  「用語ページから本文へ飛ぶ」「登録したら下の本文がリンクになる」なので、
  そこが遠くなるのは本末転倒
- **全部を SPA にしてページを消す** — 一貫はするが、deep link とスモークテストを
  作り直すことになる。ページを残しておけば、**どちらの入り口でも同じ `mount()`**
  が動くので、二重管理にはならない

**代償**: 同じ document に複数の画面が同居するので、**id が衝突しうる**
（`#root` がビューアと点検/用語ページで当たっていた。`data-ref` に変えた）。
`document.getElementById` で拾っていたものは、覆いの中では入れ物から探す必要がある。
くり返し開かれる前提になったので、**仕掛けたものを片付ける責任**も増えた
（`select-add.js` の listener とボタン、`popup.js` の二重 install）。

## 相関図の配置 —— 関係の無い語は段に混ぜない / 並びは緩和して選ぶ

**採用**: `graph.js` の配置を 4 つ変えた。

- **関係が 1 本も書かれていない語を段から外し**、区切り線の下の帯に並べる
  （`splitLonely()` / `appendLonely()`）
- 段の中の並びは、隣接ノードの平均位置へ寄せる**緩和を 12 回まわして、いちばん
  読みやすかったものを採る**（`orderRows()` / `badness()`）。出発点は入力順と、
  多く繋がっているものから幅優先でたどった順の 2 つ
- **行は中央で揃える**（左端揃えをやめた）
- **最下段どうしの弧は下へ逃がす**。ラベルは線の上ならどこでもよいので、
  ノードの箱と先に置いたラベルを避けられる場所を順に試す（`placeLabels()`）

**理由**: 18 語 18 関係の実例（『吾輩は猫である』のローカル辞書）で図が読めなく
なった。**20 語未満でも破綻する**という報告で、原因は語数ではなく 3 つ:

- **18 語のうち 6 語が孤立していた**（大町桂月・おさん・寒月 など）。段に混ぜると
  最上段が 10 語になり、繋がっている語どうしが横へ押し広げられる。図幅は 1259 px
  ——**入れ物より広く、横スクロールが出ていた**
- **最上段には「前の段」が無い**ので、平均位置へ寄せる 1 回きりの下向き整列では
  入力順のまま残る。いちばん多く繋がっている語（吾輩・6 本）が最上段の右端に
  居座り、そこから 6 本すべてが図の端まで飛んでいた
- 「対等」の一群がまとめて最下段に来るので、**同じ段の弧 8 本とラベル**が、
  段をまたぐ線が通っているのと同じ帯に折り重なっていた

直した結果は **1259 × 406 → 698 × 561**。横スクロールが消え、辞書全体
（31 語 21 関係）でも 915 px に収まる。

**力学モデルではない。** 反復するのは段の**中の並び**だけで、回数は固定
（`RELAX_PASSES`）、乱数も時刻も使わない。収束は待たず、途中でいちばん
`badness` の小さかった並びを採るだけ。同じ辞書なら毎回同じ絵になるという
性質は変わっていない。

**読みにくさは 3 つを数える**（`badness()`）: 辺どうしの交差、辺が他の箱を
貫通する数、辺の総延長。重みはこの順に効かせてある —— 線を追えなくする原因は
交差がいちばん大きく、長さは同点のときの決め手にしかならない。

**捨てた案**:

- **孤立した語を図から落とす** — いちばん狭くなるが、`?doc=` の図は「この文書に
  出てくる語」を出すと画面に書いてある。黙って落とすと嘘になる（`hidden` /
  `outside` を必ず返しているのと同じ約束）
- **語数の多い段を 2 行に折り返す** — 幅は減るが、**段が上下の関係を表している**
  ので、同じ段が 2 行に割れると別の段に見える。折り返してよいのは、上下の意味を
  持たない孤立語の帯だけ
- **交差を厳密に最小化する** — 段の並べ替えは NP 困難で、18 語でも総当たりは
  無理。緩和 + いちばん良かったものを採る形なら、回数で必ず止まる

**代償**: 孤立した語が**段の外**に出るので、「下にあるから下位」と読まれうる。
区切り線・見出し（語数つき）・凡例の 3 か所で「段の外」と書いている。
全部が孤立しているときは区切るものが無いので、線も見出しも出さない。

## 相関図は拡大縮小して動かす（入れ物ごと伸ばさない）

**採用**: `.graph-canvas` の高さを固定して `overflow: hidden` にし、svg を
入れ物いっぱい（`width/height: 100%`）に置いて、**`viewBox` を動かす**。
ドラッグで移動、ホイールで拡大縮小（押さえた点が軸）、右下に **−／全体／＋**、
図を選んでいるときは矢印キーと `＋` `−` `0`。開いたときは全体に合わせるが、
**拡大はしない**（1 語だけの図が画面を覆わないように）。

**理由**: 配置を直して 18 語の図は収まったが、**語が増えれば必ずまた溢れる**。
それまでは入れ物ごと横に伸びてスクロールバーで追う形で、どこを見ているのか
分からなくなっていた（1259 px の図を 900 px の窓で覗くと、全体像が一度も
見えない）。全体を見てから読みたいところへ寄れる、が要る。

**`viewBox` で動かす**。CSS の `transform: scale()` だと、線もラベルも画像を
引き伸ばしたようににじむ —— SVG を使っている意味が無い。`viewBox` なら文字は
文字として描き直される。

**捨てた案**:

- **スクロールのまま残して拡大率だけ足す** — 実装は小さいが、拡大したとたんに
  スクロール範囲が数倍になり、追う辛さがそのまま増える
- **力学モデルの図によくある「ノードを掴んで動かす」** — 手で整えれば読めるが、
  **置き場所を覚える先が無い**（辞書はファイルが正で、座標を書く場所を作ると
  「エディタで直接編集してよい」が崩れる）。配置は決定的に決まる、という前提とも
  食い違う
- **全体図（ミニマップ）を隅に出す** — 迷子になりにくいが、狭い画面で図の面積を
  食う。「全体」ボタン 1 つで戻れるなら、常時出しておく理由が薄い

**代償**: 入れ物がスクロールしなくなったので、**焦点の面倒を自分で見る**ことに
なった（`bringIntoView`）。Tab でノードや線をたどると焦点だけが枠の外へ出て
見失うため、焦点が入ったら見えるところまで動かしている。当たり判定
（`.rel-edge-hit`）も縮小に合わせて細ると押せなくなるので、そこだけ
`non-scaling-stroke` で一定に保っている。

**掴みは動き出してから捕まえる**（`setPointerCapture`）。`pointerdown` で
捕まえると、以後のポインタ事象と互換のマウス事象が入れ物へ付け替えられ、
**中の線を押しても click がそこへ届かない** —— 線を押しても編集ダイアログが
開かなくなった。動かした直後のクリックは飲むが、**必ず戻す**ので次は通る。

### どの関係を触っているかは、線と一言の両方で示す

**採用**: 線に乗せる／焦点が来ると、**その辺の一言も一緒に色が変わって太くなる**。
一言のほうに乗せても同じ（どちらから触っても同じ関係だと分かる）。描く層は
下から **線 → 一言 → ノード** の 3 枚。

**理由**: 一言は**線の真上とは限らない**。ノードの箱と先に置いた一言を避けて
空いているところへ逃がすので、離れた場所に載ることがある。線だけ色が変わっても
「どの関係を選んでいるのか」が読めなかった。

層を分けたのは、辺ごとに線と一言をまとめて置くと**あとに描いた辺の線が前の辺の
一言を横切る**から。文字には背景色の縁取りを付けてあるが、上から線を引かれると
縁取りごと消える（「文字が矢印の下になる」）。線は線どうし、文字は文字どうしで
重ねれば、順番によらず必ず文字が上に来る。

**代償**: 層が分かれると CSS の子孫セレクタ（`.rel-edge-group:hover .rel-edge-label`）
が届かないので、印は JS が両方に付けて回っている。また、辺の部品から `<text>` が
抜けたことで**真横・真縦の辺は幅か高さが 0 の部品**になった（外形に線の太さは
入らない）。押せるのに「大きさが無い」ことになるので、塗らない四角を 1 枚敷いて
押せる帯の大きさをそのまま外形にしている。

## 関係の下書きは 1 語ぶんでも頼める（範囲は 1 語にしない）

**採用**: 用語ページの関係欄に **✨ この語の関係を下書き** を置き、`/api/ai/relations`
に `ref` を渡すと**その語が一方の端になる関係だけ**を探す。相手は今までどおり
範囲（既定は辞書全体）から選ばれる。

**理由**: まとめての下書き（ビューアの ✨ 関係を下書き）は、文書に出てくる登録済みの語
**ぜんぶ**が対象。あとから 1 語を足したときや、特定の人物だけ関係が空のまま残った
ときに、それを埋める道が無かった。全体をもう一度回すと、すでに書いた関係を除いた
残りを探すぶんだけ待たされる（1 本あたり 20 秒ほど）。

**範囲を 1 語にはできない。** 関係は 2 語が揃って初めて書ける。だから絞るのは
**範囲ではなく出力**で、3 か所でやる:

- **頼む**（プロンプトに「かならず『〇〇』の関係にすること」）—— 落とすだけにすると、
  上限の大半を他人どうしの関係が食って肝心の語の関係が数本しか残らない
- **渡すテキストを絞る**（`cooccurrence_context(focus=…)` / `first_scene_context(focus=…)`）
  —— その語が写っていない場面を渡しても、頼んだ関係は出てこない。1 語ぶんのときは
  文書の頭出しへ落とすのもやめた（他人どうしの話が返るだけ）
- **落とす**（`filter_relations(focus=…)`）—— 禁じても返ってくることがある

**捨てた案**:

- **カテゴリ絞りで代用する** — API は前から `category` を受けるが、同じカテゴリの語が
  多ければ結局まとめて探すのと変わらない。「この語だけ」は表せない
- **相手を人に選ばせてから AI に一言だけ書かせる** — 迷いは減るが、**誰と関係が
  あるのかを探すのが下書きの仕事**で、相手が分かっているなら手で書くほうが速い

**代償**: 用語ページからの下書きは**開いているフォルダの本文**を読む（ビューアと違って
「表示中の文書」が無い）。読む範囲が画面と一致しないのは相関図から下書きを外したときの
理由と同じ形なので、**案内文に読む場所を明記**して区別できるようにしてある。

**焦点の表記は焦点として解決する**（`ai._resolve_side()`）。揺れの吸収は
`relations.resolve()` の 1 か所に任せたままで、足したのはこれだけ —— 用語ページから
頼んだときは**どのエントリの話かが画面で決まっている**（吸収する側には分からない情報）。
無いと、**別のエントリが同じ表記を別名に持っているだけで下書きが丸ごと落ちる**
（「寒月」から頼んだのに「水島」が別名に「寒月」を持っていて `resolve` が決めきれず、
1 本も残らなかった）。焦点が無いときは今までどおり寄せない。

## 交差は消せない。密なところは「一度に全部を読ませない」で凌ぐ

**採用**: 交差を無くす配置は追わない。代わりに 3 つ足した ——
**1 つの語に乗せるとその語の関係だけを濃く出す**（他は 12%）、**置き場所の無い
一言は畳んで本数を出す**（線かその語に乗せると出る）、**同じ段を結ぶ弧を段の
上下へ振り分ける**。

**理由**: 「交錯させない配置法」は**平面描画**のことで、成立する条件が 2 つある
—— グラフが平面的であること、そして**ノードを好きな場所に置けること**。この
相関図は後者を満たさない。`rank` で上下の段が決まる（「▲▼ の代わりに段で表す」）
ので、ノードは段に固定される。**層に固定した状態での交差最小化は、隣り合う 2 層
だけでも NP 困難**（Garey–Johnson）で、そもそも 0 にできる保証が無い。

しかもこの辞書では、密になる原因が並べ方ではなく**データの形**にある。「対等」の
関係は `levelsOf()` が 1 つの段にまとめるので、登場人物のように対等が多い一群は
**まるごと 1 段に載る**（実例では 16 語のうち 11 語）。1 本の直線上に n 点を置いて
その間を弦で結べば、弦は必ず折り重なる —— 実装の問題ではなく形の問題。

**やったこと**:

- **弧を上下へ振り分ける**（`arcSides()`）。段の中の関係を全部その段の上へ
  載せると、段をまたぐ線の通る帯に折り重なる。一方で反対側は空いていた。
  いちばん外側の段だけは外へ逃がし、挟まれた段は**長い弧から順に交互**
  （大きく張り出すものを同じ側に集めない）
- **一言は重なるくらいなら畳む**（`placeLabels()` の `tucked`）。重ねて出すと
  重なった 2 つとも読めず、下の線まで隠す。**消しはしない** —— 本数を凡例に出し、
  線かその語に乗せれば出る
- **1 語に乗せたらその語の関係だけ**（`installFocus()`）。畳んだ一言もここで出る

実測（辞書全体 31 語 28 関係 / epub 18 語 18 関係）で、**重なった一言の組は
どちらも 4 → 0**（畳んだのは 2 本と 1 本）。

**捨てた案**:

- **力学モデル（力の釣り合いで解く）** — 密なグラフを「それらしく」広げるが、
  段が崩れて上下が読めなくなる。乱数と収束待ちが入るので**同じ辞書でも毎回違う
  絵**になり、「昨日と同じ場所を探す」ができない
- **広すぎる段を 2 行に折り返す / 円に置く** — 幅も交差も確実に減る。**却下の
  理由は 1 つで、段が上下の意味を持っていること** —— 同じ段が 2 行に割れたり
  円になったりすると、高さの違いが上下差に見える。ここを変えるなら「上下は段で
  表す」という約束のほうを先に決め直す必要がある
- **ラベルを常に出さない（乗せたときだけ）** — いちばん静かになるが、図を一望
  して関係を読む用途が消える。**置ける一言は置く**が原則で、畳むのは置けない
  ぶんだけ

**代償**: 畳んだ一言は最初の一望では読めない。凡例に本数を出し、乗せれば出る
形にしてあるが、「全部を一度に読む」はもうできない —— それは密なグラフでは
最初から成り立っていなかった、というのがこの節の結論。

## 相関図に「交差しない見せ方」を足す（BioFabric）

**採用**: 相関図に見せ方を 2 つ持たせ、左上の選択で切り替える（選んだほうは覚える）。

- **段の図**（既定・従来）— 用語を箱、関係を線
- **交差しない図**（`fabric.js`）— **用語を横線、関係を縦線**にして、関係 1 本ごとに
  独立した列を与える。列が重ならないので**線どうしは原理的に交わらない**

**理由**: 段の図では交差を消せない（→ 前節）。消せない理由は `rank` でノードが段に
固定されているからなので、**辺のほうに場所を与える**とその制約ごと外れる。
BioFabric（Longabaugh 2012）の考え方そのままで、31 語 28 関係でも交差 0 になる。

**この辞書に合っている点が 2 つある**:

- **疎でも効く。** 隣接行列も交差 0 だが、31×31 に 28 本＝充填率 3% ではほぼ
  空白の格子になる。列は関係の数だけしか作らないので、疎なほど小さい
- **上下を捨てずに済む。** 行の並びを段（`levelsOf`）で決めれば「上にあるものが
  上位」が保てる。見せ方を変えても**言っていることが変わらない**

**捨てた案**（→ 前節で挙げた候補のうち）:

- **隣接行列** — 上のとおり、この充填率では空白ばかり
- **3 次元配置** — 任意のグラフを交差なく置けるが、平面の画面に投影した時点で
  遮蔽が起き、回さないと読めない。交差を遮蔽と操作コストに替えただけになる
- **辺の束ね / hive plot** — 見た目は整うが**交差は残る**。「交差しない表現が
  欲しい」という問いに答えていない
- **段の図を置き換える** — 全体の形をつかむのは段の図のほうが速い。**足すもので
  あって、置き換えではない**

**守っていること**:

- **形の規則は `graph-model.js` に 1 つ**（段・孤立語・並びの種）。片方の見せ方に
  写しを作ると、同じ辞書なのに違うことを言う 2 枚になる
- **分岐は `draw()` の 1 か所**。どちらも `{ root, box }` を返し、入れ物への差し込み・
  拡大縮小・凡例は共通。見せ方ごとに別の道を作ると「片方だけ拡大できない」が起きる
- **線の見た目・当たり判定・強調は同じクラスを使い回す。** `fabric.js` 側の CSS に
  足すのは形だけ。押せば同じ編集ダイアログが開く
- **凡例は見せ方ごとに変える。** 同じ文言だと、交差しない図でも「上下は段」を探す

**代償**: 全体の形（誰が中心か、どこに固まりがあるか）は段の図のほうが読みやすい。
交差しない図は**関係を 1 本ずつ確かめる**のに向いていて、一望には向かない。
だから既定は段の図のままにしてある。長い一言は列の上に縦書きで切って出すので、
全文は乗せるか `<title>` で見ることになる。

### 一言は縦書きにする（`writing-mode` は使わない）

**採用**: 交差しない図の列見出し（一言）を、**文字を立てたまま 1 字ずつ積む**縦書きに
した。`<tspan>` を 1 字ずつ置き、長音符・括弧・ダッシュ・リーダだけ SVG の
`rotate="90"` で寝かせる。

**理由**: 最初は横書きを 90 度倒していた（`rotate(-90)`）。読めるが首を傾ける必要が
あり、日本語の見出しとしては縦書きが自然。

**`writing-mode: vertical-rl` を使わなかったのは実測の結果。** SVG の `<text>` でも
効くが、**`⇄` が `⇅` に回る**（Unicode がこの記号を「縦では回す」に分類している。
`text-orientation: upright` を付けても Chrome では回った）。この辞書では `⇄` が
「相互」で、上下は `▲▼` と決めてある —— 回った矢印は**別の意味に読める**。
1 字ずつ置けば記号もそのままの向きで立ち、寝かせる文字だけを選べる。
どのブラウザでも同じに出る、という利点もある。

**捨てた案**:

- **横倒しのまま（`rotate(-90)`）** — 実装は 1 行で済むが、日本語を読むのに
  首を傾けることになる
- **`writing-mode` + `text-orientation: upright`** — 上のとおり `⇄` が回る。
  空白が 1 行ぶんの高さを食う（実測で 5 字の一言が 78px、1 字ずつなら 65px）
- **全部の記号を寝かせる / 立てる** — どちらかに寄せると、`⇄` か `ー` の
  どちらかが必ず間違った向きになる

**代償**: 字数で高さが決まるので、長い一言は見出しだけで縦に伸びる。12 字で切り、
全文は線に乗せたときの吹き出しで読ませている（`<text>` の中に `<title>` を入れると
描かれないまま文字の内容に数えられるので、そちらには入れない）。

## 相関図に「行列」を足す（NodeTrix）

**採用**: 3 つめの見せ方として行列を足した。用語を行と列に並べ、関係をマスで表す。
線を 1 本も引かないので交差という概念が無い。カテゴリの切れ目に太い線を入れる
（NodeTrix の「かたまりごとの行列」に当たる）。

**理由**: 段の図も交差しない図も、**書かれた関係しか描かない**。「まだ書いていない
組」は絵に出ないので、抜けを探せない。行列なら空きマスとして残る —— 辞書を育てる
途中で「この 2 人の関係、まだ書いていなかった」に気づける唯一の見せ方。

対角を挟んだ対称性がそのまま「相互 / 一方的」になるのも、この形でしか出ない
読み方（他の 2 つは矢印を 1 つずつ確かめることになる）。

**捨てた案**:

- **かたまりごとに別々の行列を置き、かたまり同士は線で結ぶ**（本来の NodeTrix）
  — 見た目は近いが、**行列のあいだを結ぶ線の取り回し**が要る。カテゴリで並べた
  1 枚の行列なら、カテゴリをまたぐ関係は「切れ目の外側のマス」として自然に出る
  ので、線を引かずに同じことが読める
- **関係の無い語も行と列にする** — 行も列も空になるので、語の数だけ縦にも横にも
  空きが伸びる。他の見せ方と同じく区切り線の下へ出した
- **埋まったマスだけ描く** — 軽くなるが、**この見せ方を足した意味が消える**
  （どこが空いているのか数えられない）

**守っていること**: 並びはカテゴリが主で次に段（他の見せ方と揃える）。相互は
対角の両側を埋めるが、2 つのマスは同じ 1 つの部品 —— どちらを押しても同じ編集が
開く。行と列そのものを掴めるようにし（`.mx-band`）、十字に塗るのは乗せた語だけ
（相手まで塗ると盤面の半分が色で埋まる）。

**代償**: 疎な辞書では空白が多い（31 語 28 関係で充填率 3%）。だから**関係の無い
語を外し**、カテゴリで固めて対角のまわりに寄せている。それでも一望には向かず、
「誰が中心か」を掴むのは段の図のほうが速い。既定は段の図のまま。

### 説明は図の下の枠に出す（吹き出しに頼らない）

**採用**: 図の下に**高さの変わらない枠**を置き、乗せたもの／焦点が当たったものの
説明を出す。何にも乗せていないときは案内文を出して、場所を空けたままにする。

**理由**: ブラウザの吹き出し（`<title>`）には 3 つ足りないところがある ——
**キーボードの焦点では出ない**（キーボードだけで図を歩く人には一言が読めない）、
遅れて出てすぐ消える、そして**図の中では一言を切ったり畳んだりしている**
（縦書きの 12 字、置き場所の無い一言）ので、全文が読める場所が他に無い。

**高さを固定する**のが肝。出たり消えたりで高さが変わると、下の凡例ごと動いて
読みにくい（「常に空けておけば上下して鬱陶しいのもない」）。

**捨てた案**:

- **図の上に浮かせる吹き出しを自作する** — 場所を取らないが、指した先を隠すし、
  端で回り込む処理が要る。**枠なら図を一切覆わない**
- **見せ方ごとに枠へ書きに行く** — 素直だが、見せ方を足すたびに書き足すことに
  なる。入れ物 1 つに仕掛けて `data-detail` を拾うだけにしてあるので、
  属性を付け忘れても案内文に戻るだけで壊れない
- **`title` を長くする** — 焦点では出ない問題が残る

**代償**: 枠のぶん（約 39px）縦を使う。2 行に収めて溢れたら切っている
（それでも吹き出しには全文がある）。

## 相関図に「時系列」を足す（判明位置の軸）

**採用**: 4 つめの見せ方として時系列を足した。縦軸が読み進む向き（上が先）で、
関係を**その文書のどこで読めるようになるか**の順に並べる。左に位置の見出し
（章名 / `p.42` / `L.42`）、その帯にそこで読めるようになる関係を 1 本ずつ置く。

**理由**: 他の 3 つは辞書を平らに出すので、**どの関係が先に読めるようになるのかは
絵に出ない**。ネタバレ抑止を一級の概念にしているこの辞書では、そこがいちばん
知りたい軸になる（「第一章では吾輩と主人だけ、第六章で金田家が繋がる」）。
`reveal` を書く動機も、読み返すときの道しるべも同じところにある。

**位置は「両端が出そろうところ」**（遅いほうの語の初出）。2 語が近くに並ぶ窓を
探す形にはしない —— **窓の幅という決めようのない定数**が要るうえ、「どの組にも
必ず定義できる」という性質が消える。読み手にとってその関係が読めるようになるのは
遅いほうの語が出てきた時点なので、言っていることとも合う。
（「近くに並ぶ場面」を探すのは `ai.cooccurrence_context()` の仕事。あちらは AI に
渡す本文を選ぶためのもので、目的が違う。）

**順序は計算する。保存しない。** 保存しないので**ずれようがなく**、版管理も補正も
要らない。外のエディタで本文を書き換えれば、次に開いたときの図が変わるだけ
（`read_cached()` があるので初出探しは軽い。20 語 178ms → 17ms）。**表示は人が
書いた `reveal` の文字列、並べ替えだけ計算値** —— 人の文字列で並べようとすると
「第6章」と「六章」が別物になる。

**文書が決まっているときだけ出す**（`?doc=`）。辞書全体の時系列は定義できない
（相関図が 2 つの範囲を持つ話と同じ約束）。選べないときは**黙って別の図に
差し替えない** —— 段の図に落としたことを注意書きに出し、覚えている選択のほうは
書き換えない（文書を開いて戻ったらまた時系列で出す）。

**捨てた案**:

- **行番号を保存して並べる** — 単純に見えて 3 つ破れる。epub は章名・pdf はページで
  **1 つの物差しにならない**、外のエディタで編集すると**黙ってずれる**、どの文書の
  行番号かが決まらない。順序しか要らないので、計算するなら文字位置で足りる
- **`reveal` の文字列で並べ替える** — 人が書いた表記の揺れがそのまま順序の揺れに
  なる。書いてある言葉は表示に使い、順序は計算値と分けた
- **2 語が近くに並ぶ窓を探して位置にする** — 窓幅の定数が要るうえ、並ばない組の
  位置が決まらない（落とすか、遠い場所を指すことになる）
- **同じ語を 1 つの箱にまとめて縦に線を引く** — 見た目は締まるが、行の高さが
  語の数に引っ張られて「いつ」の軸が読めなくなる。**同じ語は関係の数だけ出す**
  ことにして、1 語に乗せたら同じ語の箱を全部光らせる形で繋いだ

**代償**: 同じ語が何度も出てくる（関係の数だけ行に現れる）ので、語の一覧としては
読めない。関係の本数だけ縦に伸びるのも他の見せ方と同じで、密な辞書では長い。
**「誰が中心か」を掴むのは段の図、「抜け」を探すのは行列** —— 足すものであって、
置き換えではない。既定は段の図のまま。

## 相関図に「1 語を中心にした図」を足す（ego network）

**採用**: 5 つめの見せ方。選んだ語を真ん中に置き、**2 つ先まで**を環に並べる
（内側の環が 1 つ先、外側が 2 つ先）。まわりの語を押すとそこが中心に移り、
真ん中の語を押すと辞書ページが開く。

**理由**: 他の 4 つはどれも辞書（またはその文書）を**一度に**出すので、語が
増えれば必ず苦しくなる —— そこが 4 つに共通する穴だった。中心を決めれば絵の
大きさは**その語の近所の広さ**で決まり、辞書が何語になっても変わらない。実際の
使い方（「この人物は誰とどう関わるか」）にもいちばん近く、用語ページの関係一覧に
形を与えるものでもある。

**半径は 2**。1 だとその語に書かれた関係を並べ替えただけになり、用語ページで
足りる。2 にすると「相手の相手」＝**自分では書いていない繋がり**が見えて、図に
する意味が出る。3 以上にしないのは、密な辞書では辞書全体に近づいて取り柄
（規模に依らない）が消えるため。

**上下は捨てない。** 段の図と同じ `levelsOf()` で段を出し、中心より上の段は
12 時のまわり、下は 6 時、同じ段（対等）は 3 時と 9 時。**空いた向きは隣が
引き取る** —— 上下の語が無いときに 4 分の 1 ずつ固定で持たせると、対等ばかりの
辞書（実際よくある）で左右だけが混んで上下が空く。それぞれの向きに「いちばん
近い扇」を配れば円が埋まり、どの群も自分の向きのまわりに残る。

**捨てた案**:

- **まわりの語も辞書ページへの link にする**（他の見せ方と同じ）— 隣を覗くたびに
  図から出ることになる。押すと中心が移り、**もう一度押すと辞書ページ**なら、
  たどりながら読める（中心だけが link）
- **一言を全部の線に出す** — 線は全部中心に集まるので、外周まで出すと文字が
  折り重なって**重なった 2 つとも読めない**。中心につながる線にだけ出し、
  残りは畳む（本数は凡例に出るし、線かその語に乗せれば出る）
- **一言を線の真ん中に置く** — 根元（中心のそば）で一言どうしが重なる。
  62% ほど外側に置くと散る
- **力学モデルで置く** — 環にすれば「中心からの遠さ」がそのまま半径になる。
  乱数も収束待ちも要らない（段の図と同じ理由）

**代償**: 一度に見えるのは近所だけなので、**全体の形は掴めない**（それは段の図
の仕事）。2 つ先が多すぎるときは 60 語で切る —— 切ったことは凡例に出す。
`?ref=` で名指しされたときは覚えている見せ方を押しのけて中心の図で開くが、
**覚えているほうは書き換えず**、押しのけたことを注意書きに出す。

## 文体（口調）は指定できる。ただし効くのは人が読む文章だけ

**採用**: ⚙ の AI タブに自由記述の欄を 1 つ置き、その文字列を下書きの
プロンプトに 1 節として差し込む（`ai.build_style_block()`）。「講談調で」
「司馬遼太郎のような史伝の筆致で」「TRPG のルールブック風に」と書けば、その調子で
書かれる。

**理由**: 辞書の読み味は作品ごとに違う。小説の登場人物欄が事務的な説明文なのは
興ざめだし、TRPG のルールブックなら卓でそのまま読み上げられる調子が要る。
プロンプトに一節足すだけで届く範囲なので、専用の機能を作るより自由記述が広い。

**効く範囲を切ったのが要点** —— 要約・本文・使用例と、関係の一言 (`label` /
`back`) だけ。用語名・読み・別名・カテゴリ・タグ・関係の相手・`rank`・`reveal` は
崩させない。**好みの問題ではなく、崩れると黙って壊れるから**:

- `term` は**文書中の表記と一致しないと `filter_candidates()` が落とす**
  （登録しても本文でリンクにならないため）。文体に合わせて言い換えられると、
  頼んだ側には「なぜか候補が 1 つも出てこない」としか見えない
- `from` / `to` も一覧の表記と一致しないと `filter_relations()` が落とす。
  こちらは**関係が 1 本も残らない**
- カテゴリはディレクトリ名になる（使える文字と長さに制限がある）

範囲は**毎回プロンプトに書き添える**。文体だけを渡して出力側で弾く形にすると、
落ちた理由が「AI が指示どおりに書いただけ」になり、直しようが無い。

**抽出には効かせない**。抽出が返すのは本文にある表記そのままなので、混ぜても
得るものが無く、崩される危険だけが増える。

**ネタバレの約束は変わらない**。この辞書のネタバレ抑止は「**渡すテキストそのもの**
で担保する」上に立っているので、「結末をほのめかす調子で」と書いても、`first` で
AI に届くのは初出の場面だけ。プロンプトの節としては「ネタバレの禁止」と「出力形式」
のほうが優先すると明記してあるが、**それが担保ではない**。

**置き場所は辞書と同じ `.glosspop`**（`style.md`）。口調は**作品につく**ので、全体に
1 つだけ持たせると、小説を読むフォルダと社内資料のフォルダを行き来するたびに ⚙ を
開き直すことになる。辞書と同じ場所にすると 3 つが自動で揃う ——
**祖先方向に探すので巻をまたいで効く**、**フォルダごとコピーすれば口調も付いてくる**、
**効く範囲が辞書とずれない**。優先順は 環境変数 > 📁 このフォルダ > 全体 > 既定。

**基準は「いま読んでいるもの」で、エントリの保存先ではない。** `scope: "auto"` は
語ごとに行き先が変わるので、保存先で切り替えると **1 回の「まとめて登録」の中で
口調が混ざる**。

**中身がそのまま値の素のテキスト**にしたのは、引用符やエスケープを挟まずにエディタで
書けるようにするため（「エディタで直接編集してよい」がこの辞書の売り）。読むたびに
開くので、書き換えれば次の下書きから効く。

**書き込みは専用の口 (`PUT /api/ai/style`) だけ**にしてある。📁 はフォルダに
`.glosspop` を作りうるので、モデルを選び直したついでに書かれると「開いただけの
フォルダを汚さない」が崩れる。画面でもボタンを分けた（⚙ の「保存」がデータの
保存先のもので、AI の保存とは別なのと同じ理由）。

**捨てた案**:

- **文体を選択肢（ラジオボタン）にする** — 「広川太一郎風」も「うちの製品の
  ドキュメント調」も同じ欄で書ける自由記述のほうが広い。選択肢は**例**として
  押せるようにして、押せば入力欄に入るだけにした（`ai.STYLE_PRESETS`）
- **1 回ごとに文体を選ばせる** — まとめて登録は「抽出 1 回 + 下書き N 語ぶん」で、
  語ごとに違う口調にしたい場面が無い。辞書の中で口調が混ざるほうが困る
- **`llm.resolve()` に入れる** — 文体は「何を頼むか」で、提供元・モデル・思考の
  深さ（「誰にどう頼むか」）とは別の話。同じ画面に出るというだけの理由で
  `llm.py` に入れると、提供元を足すたびに文体が付いて回る
- **設定ファイルに「フォルダ → 文体」の対応表を持つ** — フォルダを移動・コピー
  した瞬間に切れる。辞書がフォルダについていくのが売りなので、口調も一緒に行く
- **`categories.yaml` に足す** — カテゴリマスターは並びと説明の正。混ぜると、
  取り込みの併合規則（「手元の並びは保つ」）に文体まで巻き込まれる
- **文体を辞書の書き出し (zip) に入れる** — 📁 のぶんはフォルダごと運ぶもので、
  全体のぶんは設定ファイル。入れると「置き換え」で消える範囲が広がる
- **画面をフォルダ側と全体側で分ける（辞書一覧に置く）** — 文体を探す場所が
  2 つになる。1 つの欄に**保存先の選択**を付けたほうが、優先順を並べて見せられる

**代償**: 途中で変えると**辞書の中で口調が混ざる**。これは 1 語ずつ書き直せる
ようにした（編集ダイアログの「✨ AI で書き直す」）—— **一括で書き直す口は作らない**。
本文は人が直せるものなので、まとめて AI に書き直させる経路を足すと「直したはずの
手書きが消えた」を生む。1 語ずつなら、保存する前に読んで止められる。

書き直しでは**いま書かれている説明を渡し、事実は変えさせない**。編集中は選択
テキストも文書も手元に無いので、渡さないと AI は用語名だけを頼りに一般論を書く
（＝人が手で直した内容が丸ごと消える）。差し替えるのは要約と本文だけで、
**使用例は残す** —— 選択して登録したものは本文からそのまま採った引用なので、
書き直すと引用でなくなる。
置き場所が 2 つに増えたぶん**「どちらが効いているか」を必ず画面に出す義務**が
生まれた（押しのけられた側の値も返している）。URL を読んでいて、その URL の辞書が
まだ無いときは 📁 を選べない —— **URL 側は辞書を勝手に作らない**ので、置き場所が
決まらない（全体の指定に落ちる）。
