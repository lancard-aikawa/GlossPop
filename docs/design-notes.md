# 設計メモ

なぜそうなっているか。コードを読めば「何をしているか」は分かるが、「なぜ他の案を
採らなかったか」は残らないので、ここに書く。決まったことは消さずに積む。

## 辞書の保存形式: 1 用語 = 1 Markdown ファイル

**採用**: `data/glossary/<カテゴリ>/<slug>.md`（YAML frontmatter + 本文）

**理由**: 辞書は Claude にも人にも読ませたい。SQLite だと差分レビューも手編集も
できず、Claude に読ませるには変換が要る。Markdown なら本文がそのまま定義文になり、
`git diff` が意味のある単位で出る。数百件までは全ファイル読み込みで十分速い。

**捨てた案**:
- SQLite — 検索は速いが、手編集と差分レビューを失う代償が大きい
- 単一 JSON — 単純だが、複数箇所を同時に触ると競合しやすい

**代償**: 件数が数千を超えると `load_all()` が重くなる。そのときは mtime キャッシュ
（実装済み）だけでは足りないので索引を別に持つことになる。

## カテゴリ = ディレクトリ

**採用**: ディレクトリ名がカテゴリの正。frontmatter には書かない。

**理由**: 正が 2 箇所にあると必ずずれる。ファイラで見たときに分類が見えるのも利点。
`mkdir` しただけのディレクトリはマスターへ自動で取り込む。

**代償**: カテゴリ名がファイルシステムの制約を受ける。そのため
`models.normalize_category()` で全 OS の共通部分に絞り、NFC 正規化している
（macOS が NFD で返す濁点をそのままディレクトリ名にすると、Windows/Linux と
別物になる）。

**サブカテゴリはディレクトリにしていない**。2 段にすると移動と改名の組み合わせが
増える割に、得られるのは表示上のグルーピングだけで、それは frontmatter でも足りる。

## 一意キーは「カテゴリ + 用語」

**採用**: 同じ用語名でもカテゴリが違えば別エントリ。衝突判定は同一カテゴリ内だけ。

**理由**: 「ソース」がプログラミングにも料理にもある、という状況が実際に起きる。
用語名だけを一意キーにすると、片方を登録できないか、名前を歪めることになる。

**波及**: `find_by_surface()` がリストを返す。自動リンクは「表記」を `data-gloss` に
持たせ、吹き出し側が表記から全件を引く。リンク先は 1 件なら詳細ページ、複数なら
一覧検索。

## 同名が複数あるときの吹き出し: アコーディオン

**採用**: カテゴリごとの `<details>`。先頭だけ開く。1 件のときは従来どおりの見た目。

**捨てた案**:
- ヘッダにタブを並べる — 幅 360px の吹き出しでは、カテゴリ名が長い / 件数が多いと
  あふれる
- 全部を縦に展開 — クリック不要だが、本文が長いと吹き出しが壁になる
- 2 段階（一覧 → 選んで詳細） — 小さく収まるが、1 件目を読むのにも 1 クリック要る

`<details>` はネイティブでキーボード操作とスクリーンリーダーに対応するので、
自前のタブ実装より安い。

## AI 連携: Claude Code CLI をサブプロセス起動

**採用**: `claude -p` を `subprocess.run()` で叩く。

**理由**: API キーを別途用意させたくない。Claude Code の認証をそのまま流用できる。

**代償**: 1 回 10〜30 秒かかり、並列性も低い。UI は「数十秒かかります」と明示して
待たせる作りにしてある。

**踏んだ罠**: プロジェクト内で実行すると CLAUDE.md と `gloss-add` スキルを読み込み、
「重複確認のため CLI を実行させてほしい」と要求して承認待ちで固まる（非対話なので
永久に返らない）。プロジェクト外の cwd で、全ツールを禁止して呼ぶ必要がある。
詳細は [CLAUDE.md](../CLAUDE.md)。

## 自動リンクの照合単位: 「読者に見えるテキスト」

**採用**: HTML を走査してインライン要素をまたいだテキストを組み立て、そこで照合する。
一致がノードをまたぐ場合は断片ごとに `<a>` を張り、CSS で下線を繋げる。

**理由**: 最初はテキストノード単位で照合していたが、`**冪**等` のように装飾が語を
分断していると一致しなかった。読者には「冪等」に見えているのにリンクされないのは
バグにしか見えない。

**境界**: ブロック要素と `<br>` はまたがない。またぐと `<p>冪</p><p>等</p>` が
偶然一致してしまう。

**捨てた案**: クライアント側で DOM を走査して置換する。サーバ側でやるほうが
テストしやすく、辞書ページとビューアで実装を共有できる。

## インラインコードはリンク対象、コードブロックは対象外

**採用**: `` `用語` `` はリンクする。``` ``` ``` フェンスと `<pre>` はしない。

**理由**: 日本語の技術文書ではバッククォートを「コード」ではなく用語の強調として
使うことが多い。README 内の `` `機械学習` `` がリンクされないのは期待外れになる。
実際のコードを載せるのはコードブロックのほうなので、そこで線を引ける。

**代償**: コード片の中の識別子が拾われることがある。実例として、別名 `MD` が
`.md` という拡張子に当たる（→ [open-questions.md](open-questions.md)）。

## 辞書本文は保存時に 1 文 1 行へ整形

**採用**: 60 字を超える行を句点で割って保存し、表示側は単一改行を `<br>` にする。

**理由**: AI は 1 段落に 5〜6 文を詰め込みがちで、そのまま出すと読みづらい壁になる。
保存時に整形すると、ファイル自体が読みやすくなり `git diff` も文単位になる。

**触らないもの**: ビューアで開くソース文書。ユーザーの `.md` を勝手に整形しない。
そのため markdown インスタンスを 2 つ持っている（`breaks` の有無）。

## 外部 HTML は許可制でサニタイズ

**採用**: 標準ライブラリの `HTMLParser` で、残すタグ・属性を列挙する方式。

**理由**: 依存を増やしたくない。許可制なら未知のタグ・属性は必ず落ちる。
`<main>`/`<article>` を優先して本文だけ採るので、ナビゲーションや広告が混ざらない。

**代償**: 完璧なサニタイザではない。JavaScript で描画するページは本文が取れない
（その旨をエラーメッセージに書いてある）。ローカル専用ツールなので localhost や
社内ホストも意図的に許可している。
