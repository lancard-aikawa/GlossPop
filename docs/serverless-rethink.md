# サーバを運用しない前提で引き直す（実験の記録）

[mobile-rethink.md](mobile-rethink.md) の続き。あちらは**携帯前提で引き直した**記録で、
その結論は「**辞書はサーバに置く / オンラインが主**」だった。ここはその**前提そのものが
覆った**ときの記録。

**まだ決めていない。** 決まったのは方針（サーバを運用しない）と、**実験の結果**だけ。
最終形は選んでいないので、[GlossPopApp](../../GlossPopApp/) の実装はまだサーバ版のまま。

## なぜ引き直すのか

技術的な理由ではなく、**運用の理由**。挙がったのは 6 つ:

- **狙われやすい。** 公開したサーバは、それ自体が守り続ける対象になる
- **アプリとサーバの 2 点管理**が要る
- **プロジェクトごとにサーバが増える。** 1 本ずつは小さくても、積み上がると運用の負担になる
- **全体の管理権限が無い。** 止める権利も無い
- **属人・属グループ化**を招く
- **デプロイ方法が断片化する。** 行き先が変わる・複数ある・そのときの状況に左右される ——
  経路が増えること自体が問題

**どれも「サーバがある」ことの帰結で、機能の話ではない。** だから機能を削るのではなく、
サーバを要らなくする方向で考える。

## 失うものを取り違えない

サーバを捨てると消えるとされたのは アカウント / 引き継ぎ / グループ / マネージド AI
だが、**それらが要求しているのはサーバではない**:

| 失うとしたもの | 実際に要るもの |
| --- | --- |
| アカウント・引き継ぎ | 識別と保存先 |
| グループ（共有辞書） | 共有できる保存先と権限 |
| 複数端末 | 同期できる保存先 |
| **マネージド AI** | **秘密を持てる場所** ← これだけ本当に別 |

要るのは**保存先と識別**であって、**自分の計算機ではない**。自前サーバが要っていたのは
**照合（`Linker`）をサーバでやっているから**で、そこをクライアントへ移せば残るのは
置き場所だけになる。

だから最初に確かめるべきことは 1 つに絞られた ——
**`glosspop.core` はクライアントで動くのか。**

## 実験: Pyodide で `glosspop.core` を動かす

Pyodide は CPython を WebAssembly にしたもの。**同じ `core` の**ソースがそのまま動けば、
写しを作らずに済む（この 2 プロジェクトでいちばん守っている線）。

### 動いた。無改造で

| 見たもの | 結果 |
| --- | --- |
| `glosspop.core` の import | OK（**ソースは 1 文字も変えていない**） |
| pydantic のモデル検証 | OK |
| 照合 — 最長一致が勝つ | OK |
| 照合 — `API` が `rapid` に当たらない | OK |
| 照合 — 別名が効く | OK |
| `render`（markdown-it） | OK |
| `entryfile` の往復 | OK |
| **`archivefmt` の zip 往復** | OK（GlossPop と同じ形のまま） |

**pydantic が最大の関門だったが、開いた。** `core` の外部依存は
`pydantic` / `PyYAML` / `markdown-it-py` / `mdit-py-plugins` の 4 つで、非純 Python は
pydantic だけ。Pyodide が `pydantic_core` の WASM wheel を配っているので、そのまま載る。
**`core` から pydantic を外す前段は要らない。**

### 速さ（2026-08-07 実測）

`native` はこの PC の CPython、`PC` は同じ PC の Chrome、`g05` は moto g05（Android 15）。

| | native | PC (Pyodide) | g05 (Pyodide) |
| --- | --- | --- | --- |
| Pyodide の起動（WASM） | — | 1,687 ms | **7,886 ms** |
| pydantic / pyyaml | — | 225 ms | 1,024 ms |
| markdown まわり | — | 360 ms | 1,589 ms |
| `glosspop.core` の import | — | 557 ms | **2,905 ms** |
| **→ 画面が出せるまで** | — | **2,840 ms** | **13,538 ms** |
| `Linker` 組み立て（300 語） | 31 ms | 63 ms | 301 ms |
| `Linker` 組み立て（3,000 語） | 300 ms | 531 ms | **2,466 ms** |
| 照合 4 万字 | 7 ms | 11 ms | 66 ms |
| **照合 34 万字**（長編 1 冊） | 55 ms | 112 ms | **503 ms** |

- **PC では native の約 2 倍。** 素直な数字
- **g05 では PC の約 5 倍。** 全項目でほぼ一様に効くので、CPU の差そのもの
- **読んでいる最中は待たされない。** 長編 1 冊を丸ごと照合して 0.5 秒、1 章なら 66 ms
- **辞書が大きいと組み立てが効く**（3,000 語で 2.5 秒）。ただし辞書が変わったときだけなので、
  `store` の署名でキャッシュする今の作りがそのまま効く

### 大きさ

**13.6 MB**（WASM 本体 9.2 + 標準ライブラリ 2.4 + pydantic 等 2.0）。
純 Python の wheel（markdown-it 系）は合計 0.19 MB で誤差。
殻に同梱するなら誤差、PWA なら初回だけの負担。

### 残った問題は 1 つだけ ——起動

**g05 で 13.1 秒**（通信はローカル）。以下、そこを掘った記録。

**実行ごとに 1〜1.5 秒ぶれる。** 小さい差を読み取らないこと。

## 起動をどこまで縮められるか（実測）

### まず、測り方を間違えていた

最初の計測は静的サーバに `Cache-Control: no-store` を付けていた。これは
**ブラウザの WASM コンパイル結果のキャッシュまで捨てる**ので、毎回「初回」の値になる。

直して測り直すと、2 回目の起動は **8,835 → 6,837 ms**（−2.0 秒）。
**wasm と wheel はキャッシュさせること。**

### 内訳（g05・キャッシュ後・合計 13,083 ms）

| 段 | 実測 | 縮められるか |
| --- | --- | --- |
| **WASM + CPython の初期化** | **6,837 ms** | **✗ 床** |
| パッケージの読み込み（pydantic / yaml / markdown） | 2,973 ms | ○ 同梱すれば大半が消える |
| `glosspop.core` の import | 3,210 ms | ○（下記） |
| └ `import glosspop.core.models` | **1,578 ms** | ○ **pydantic のモデル構築** |
| └ `import pydantic` | 604 ms | ○ 同上 |
| └ `import markdown_it` / `yaml` | 936 ms | △ 読むまで要らないので遅延できる |
| └ `import glosspop.core.linker` ほか | 92 ms | — 誤差 |

**6.8 秒はコンパイルではなく CPython の初期化**（インタプリタの構築、標準ライブラリの展開）
なので、キャッシュの対象にならない。**Pyodide である限り動かない床。**

**いちばん効くのは `core` から pydantic を外すこと**（約 2.2 秒）。次がパッケージの同梱
（約 3 秒）。両方やって **13.1 → 7〜8 秒**が現実的な上限。

**`models.py` が重いのは `.py` の解析ではなくモデルの構築。** `BaseModel` 5 つと
`field_validator` 12 個ぶんのバリデータを組む代金なので、`.pyc` を同梱しても効かない。

## 隠せるか（実測）

「用意ができるまで」は待たせても、**押してから待たせなければよい**。
Pyodide を **Web Worker** に置き、UI は素の HTML/JS で即出しにして測った。

### 画面の固まりは完全に消えた

| | g05 | PC |
| --- | --- | --- |
| HTML が描かれるまで | **235 ms** | 14 ms |
| **主スレッドが止まった最長** | **15 ms** | 19 ms |
| 描いたフレーム数（約 30 秒） | 2,736 | — |

12.9 秒温めている間ずっと、**主スレッドの停止は最長 1 フレーム**。
スクロールも入力も引っかからない。**「重いアプリ」の印象は避けられる。**

### ただし、押した時刻がそのまま待ち時間になる

温まりきるのが **12,876 ms**。それ以前に押すと、残り時間ぶんそのまま待つ。

| 押した時刻 | g05 で待たされた時間 |
| --- | --- |
| 1 秒後 | 11,855 ms |
| 5 秒後 | 7,856 ms |
| 10 秒後 | 2,856 ms |
| **20 秒後** | **73 ms** |
| 30 秒後 | 71 ms |

温まったあとは **73 ms**（1 章ぶん）で体感ゼロ。
**つまり隠せているのは「固まらないこと」だけで、待ち時間そのものは隠せていない。**

### 分かったこと 3 つ

1. **`core` はブラウザで無改造のまま動く。** 照合の速さも問題にならない（1 章 68 ms）
2. **UI の固まりは Worker で完全に消せる**
3. **温めの床は 7〜8 秒**（削れるだけ削って）。**押すのが早い人には隠しきれない**

7〜8 秒なら「URL を貼って押す」までの実時間とだいたい釣り合うが、
**しおりの 1 タップには間に合わない。**

## 何が要らなくなるか

サーバを配信元に置かないなら、そのために作ったものは意味を失う:

- **App Links と `assetlinks.json`** —— メールの使い捨てリンクをアプリで受けるための仕掛け。
  引き継ぎが無くなれば不要
- **`accounts.py` / `identity.py` / `mail.py`** —— 1 台 1 人になるので役目が消える
- **DEVELOP.md の「配信元サーバを用意する」** —— 手順そのものが不要になる

**まだ消していない。** 最終形が決まっていないうえ、消すのはいつでもできるから。

## 決めていないこと

### 1. 起動の 7〜8 秒をどう扱うか

**縮める余地は測り切った**（上記）。**隠す余地も測り切った** —— 固まりは消せるが、
待ち時間は消せない。残っているのは**受け入れるかどうか**の判断だけ。

選択肢は 3 つ:

- **受け入れる。** 削るところまで削って 7〜8 秒。UI は固まらない
- **入口を変える。** 「開いてすぐ 1 タップで読み始める」動線（しおり）をやめ、
  貼る・選ぶ手間を挟む形にして、そのぶん温める
- **Pyodide をやめる。** Chaquopy（ネイティブ Python）なら床が消えるが、
  **Android 専用**になり +20〜40MB。`app.py` 以下がそのまま動く利点はある

### 2. 保存先（identity と共有をどこから借りるか）

**`core` がクライアントで動くと決まったので、backend は「置き場所」だけでよくなった。**
候補は 2 つ:

- **利用者のストレージ / git リモート** —— 辞書はもともと `<カテゴリ>/<slug>.md` の
  テキストの集まりなので、git に置けば 識別・同期・**グループ**（コラボレータ）・履歴が
  そのまま手に入る。**運用するものはゼロ。** 資格情報は利用者が貼る PAT で、
  Gemini の BYOK とまったく同じ形
- **マネージドの BaaS**（Supabase / Firebase / Cloudflare）—— OS もパッチもデプロイも無い。
  ただし**プロジェクトごとに 1 つ増える**ので、上の不満のうち「乱立」だけは残る

**前者のほうが条件にも、この辞書の作り（ファイル・テキスト・zip・外のエディタで編集してよい）
にも合う。**

### 3. URL を読む機能をどうするか

**純粋な PWA では、任意のサイトを取得できない**（CORS）。回避には中継サーバが要り、
振り出しに戻る。

| | 純 PWA | 殻（Capacitor） |
| --- | --- | --- |
| 貼り付け・手元のファイル | ○ | ○ |
| **URL を投げて読む** | **✗** | ○（ネイティブ HTTP なので CORS が無い） |

**殻が本当に買っているのはこれ**であって、店に並べることではない。
「読む」を残すなら殻が要る、と分かった。

なお **PWA を先に作り、あとから殻で包む道は作り直しにならない** ——
どちらも「WebView の中で同じ Python が動く」構成で、殻が足すのは取得の橋 1 本だけ。

### 4. マネージド AI

**秘密を持てる場所が要る**ので、ここだけはサーバか関数 1 本が要る。
当面は BYOK のままにして、課金を始めるときに考える。

## 実験のやり直し方

スパイクは使い捨てにした（scratchpad）。やり直すなら:

1. `npm install pyodide` して `loadPyodide()`
2. `loadPackage(["pydantic", "pyyaml", "micropip"])`（Pyodide 同梱）
3. `micropip.install` で `markdown-it-py` / `mdit-py-plugins` / `linkify-it-py` /
   `mdurl` / `uc-micro-py`（純 Python）
4. `glosspop/__init__.py` と `glosspop/core/*.py` を zip にして `unpackArchive`、
   `sys.path` に足す

測るときに踏んだ落とし穴 3 つ。**どれも落ちずに黙って値を狂わせる:**

- **静的サーバはスレッド化する。** 単一スレッドだと、WASM と標準ライブラリを並行して
  取りに来たところで**止まる**
- **`Cache-Control: no-store` を付けない。** WASM のコンパイル結果のキャッシュまで捨て、
  **起動が毎回「初回」の値**になる（2 秒ぶん悪く出た）
- **Pyodide の `stdout` を潰さない。** `loadPyodide({stdout: () => {}})` にすると
  Python 側の `print` が消え、**結果が出ていないのかエラーなのか分からなくなる**
  （戻り値で受け取るほうが確実）
