# 未解決 / 保留

決めたら [design-notes.md](design-notes.md) に移して、ここからは消す。
**やったこともここから消す**（残っていると「まだ無いもの」に見える）。

## 1. 検索の初回だけは全文書を読む

解釈済みの文書を使い回すようにしたので、2 回目以降は速い（epub 10 冊で
108ms → 12ms。→ [design-notes.md](design-notes.md)）。**残っているのは初回**で、
そこは全文書を解釈するぶんそのままかかる。

真面目な索引（どの語がどのファイルにあるか）を持てば初回も消せるが、**索引は
ずれると嘘をつく**。いまの作りは「毎回すべてのファイルを見て、変わっていない
ものを読み直さないだけ」なので取りこぼしようがないが、索引にすると取りこぼしが
**「その語は無かった」と区別が付かなくなる**（打ち切りを必ず返しているのと同じ話）。
初回の重さと引き換えにする価値があるかは、**実際に重いと感じてから**決める。

## 2. Windows 以外の配布

`packaging/` は PyInstaller の Windows onedir だけ。macOS / Linux は「ソースから
動かす」しか道が無い。`appwindow.py`（ブラウザのアプリモード）と `picker.py`
（tkinter の別プロセス起動）は書き分けてあるので動きはするはずだが、**確かめていない**。

## 3. スモークテストが CI でたまに落ちる

`test_the_glossary_filters_by_tag` が **v0.6.0 のリリースで落ちた**（623 passed /
1 failed。再実行では通ったのでフレーク）。`/glossary` を開いて `.card` が 15 秒
出てこない、という落ち方。手元と `check.cmd ci` では再現していない。

**この落ち方をする本物のバグを 1 つ見つけて直した**（カテゴリ管理が、読み込みの
前に開かれると「カテゴリがまだありません」のまま**描き直さない**）。応答を止めて
おく形の再現テストを足してあり、直す前は**まったく同じ「要素が 15 秒出てこない」**
で落ちる。手元では一瞬で返るので絶対に踏まず、負荷の高い CI でだけ出る類。

ただし**落ちたのは別のテスト**（`test_the_glossary_filters_by_tag`）なので、
**これが原因だったという証明にはならない**。残っている筋は「一覧の描画が
`/api/categories` と `/api/tags` の完了を待っている」こと —— どちらかが返って
こないと `.card` が永久に出ない。直すなら一覧を先に描いて絞り込みを後から
埋める形になるが、`?category=` の初期選択が効くまでに一度絞り込み無しの
一覧が見えるので、**見た目の代償のほうが大きい**。次に落ちたときに判断する。

見るための足場は入れてある:

- `page` fixture が JS の例外・console の error・通信の失敗を集めて出す（`_watch_page`）
- 一覧を待つのは `open_glossary()` 経由にした。`#list` が「busy でない かつ
  中身がある」まで待ち、**中身がエラーならその文言を持って落ちる** ——
  以前は読み込みが失敗しても素のタイムアウトになり、理由が残らなかった

**回数を増やすのではなくテストを決定的に書き直すこと**（`check.cmd ci` の
繰り返しは網であって証明ではない）。遅らせて再現するときも `sleep` ではなく
**応答を止めて手で通す** —— `sleep` で作った再現は、それ自体が次のフレークになる。

## 4. 時系列で「位置を手で直す」ことはできない

時系列そのものは入れた（→ [design-notes.md](design-notes.md)）。位置は毎回本文から
数えていて**保存していない**ので、ずれようがない代わりに**人が直す口が無い**。
残っているのはそこと、読書位置と繋ぐ話の 2 つ。

- **人が位置を手直ししたいとき。** `reveal` が本文にあるラベル（「第六章」「p.42」）
  で書けるなら、`Document.segments` から毎回引き直せるので**ずれない**。脆いのは
  **ラベルの無い文書（素のテキスト・Markdown）で位置を指したとき**だけ。ここに
  限って保存 + 版管理 + 補正が要る。設計は決めてある:
  - **版の鍵はハッシュ。** `read_cached()` の path + mtime + size は「読み直すか」の
    判定で、**内容が同じ保存し直しでも変わる**（補正を促す判定に使うと空振りする）。
    `documents.decode()` を通した**後**の本文のハッシュなら、文字コードや CRLF↔LF で
    版が変わらない。二段構えで安く済む（stat が同じ → 何もしない / 違う → ハッシュを
    取り、同じなら stat だけ更新）
  - **版が違ったら古い位置で並べない。** 「更新されています。補正してください」と
    出して順序を落とす。古い位置でそれらしく並べるのがいちばん危ない
  - **補正は報告を出す。推測で埋めない。**「同じ N 件 / 動いた M 件（前 → 後）/
    見つからなくなった K 件」。見つからないものは空にして残す（消さない）
  - **入り口は点検（`/doctor`）。**「直さないと読み手に見えないもの・黙って壊れて
    いるもの」を挙げる場所で、一段落してから自分で走らせる運びにも合う
  - **置き場所は frontmatter の外。** 派生データだし、`relations` は手で書ける形を
    保ちたい。**無くても壊れない**（時系列が出ないだけ）ようにする
- **「いま読んでいるところまでの関係だけ出す」。** 強力だが単位が違う ——
  読書位置は `progress.js` が**描き終わった本文のブロックの添字**で持ち、サーバは
  文字位置。揃えるのに一手要るので、時系列そのものとは分けて考える

## 5. 相関図の「関係が書かれていない語」は、伏せた結果 0 本になった語まで含む

`splitLonely()` は**伏せたあとの辺**で数えているので、判明位置つきの関係しか
持たない語が「関係が書かれていない語」の帯へ落ちる。**関係は書いてあるので、
画面の文言が嘘になる**。

`samples/坊っちゃん` で実際に出る（既定の表示で うらなり・マドンナ・港屋・養源寺・
ターナー島 の 5 語が帯に並ぶが、この 5 語はいずれも関係を持っている）。

直すなら 2 通り:

- **数え方を変える**（伏せる前の辺で孤立を判定する）。ただし帯に落とさないと、
  辺の無いノードが段の中に浮いて図が横に広がる —— `splitLonely()` を足した理由が
  そこなので、代わりの置き場所が要る
- **文言を変える**（「いま出ている関係が無い語」など）。安いが、伏せていないときも
  その文言になる

**どちらにせよ「伏せたせいで落ちた語が何語か」は出したい** —— `hidden` の本数を
返しているのと同じ約束で、黙って別の見出しの下に置かない。

## 6. AI の応答が途中で切れると、そのまま失敗する

`parse_draft()` / `parse_candidates()` は JSON を取り出せなければ落ちる。
**応答が途中で切れた場合も同じ扱い**になり、502 が返るだけで引き直さない。

`samples/坊っちゃん` を作る途中で 1 回踏んだ（12 語のうち 1 語で、`definition` の
文字列が閉じないまま応答が終わった）。押し直せば通るので UI では致命的ではないが、
**まとめて登録**の途中で 1 語だけ落ちると分かりにくい。

`llm.TransientError` は**提供元の失敗**（503 / 429）を見ているので、ここは層が違う。
入れるなら「JSON として読めなかったときだけ 1 回引き直す」で、`_generate()` を
呼ぶ側（`ai.py`）の仕事になる。**恒久的な失敗まで引き直さない**線は同じ。

## 7. 用語ごとの画像（ペルソナの顔とは別）

語り手の顔は入れた（辞書に 1 枚。→ [design-notes.md](design-notes.md)）。
**用語ごとの画像**（赤シャツの肖像、道具の写真）は入れていない。

- 欲しがる人は多いはずだが、**吹き出しの同じ場所を取り合う**。主戦場は用語ページ
  （広い）で、吹き出しは従になる
- 置き場所は `<辞書>/images/<slug>.<拡張子>` あたりが素直（カテゴリ名を挟むと、
  カテゴリを移したときに画像だけ取り残される）
- **配る口はペルソナと同じ規則で**（パスを外から受け取らない・SVG は通さない・
  URL に更新時刻を入れる）。ここを緩めると、任意のファイルを配る口になる
- **受け取る口もペルソナと同じ規則で**（ファイル名は受け取らず、拡張子は中身から
  決める・上限を持つ）。ただし用語ごとだと**名前が用語ごとに変わる**ので、
  「決め打ちの名前」で逃げられない —— `slug` から組み立てた結果が辞書の中に
  収まっているかを最後に検査することになる（控えの `_backup_path` と同じ形）

## 8. 相関図の中の文字だけは「文字の大きさ」に付いてこない

⚙ の **表示 → 文字の大きさ** は画面全体に効くが、**相関図の SVG の中だけは生の px の
まま**（→ [design-notes.md](design-notes.md)）。図には拡大縮小があるので手段はあるが、
「ここだけ効かない」ことに変わりはない。

- 塞ぐには、**CSS の px を JS 側の見積もりへ渡す**必要がある（`base.js` の
  `estTextWidth` の既定 11、`svgVerticalText` の `lineHeight`、`graph.js` の
  `labelBox`）。描く前に `getComputedStyle` で 1 回読んで配るのが素直
- **CSS だけ var 化するのがいちばん危ない。** 避けたはずのラベルが重なり、縦書きの
  列から文字がはみ出すのに、**図は描けてしまう**（テストも画面も「壊れた」と言わない）
- 5 つの見せ方が同じ計算を使うので、直すなら 1 か所で済む —— 逆に、**どれか 1 つの
  見せ方だけで試すと残り 4 つで崩れる**

## 9. 地図の上に置く見せ方（歴史戦記・イフもの・日記）

**これは新しい仕組みではなく、相関図の 6 つめの見せ方。** 分岐は `draw()` の 1 か所、
`{ root, box }` を返す、形の規則は `graph-model.js` —— 既存の 5 つとまったく同じ枠に
収まる。「位置で置く図」。

**新しく要るデータは座標 1 つだけ。**「〇〇から✕✕まで」は**既に `relations` そのもの**
（向き `to`・一言 `label`・上下 `rank`・相互 `back` が揃っている）。進軍経路は
**地名エントリどうしの関係**なので、データモデルの追加は要らない。相関図の辺をそのまま
地図の上に引く。

**時系列 × 地図 = 進軍。** `timeline.py` は既に「両端が出そろうところ」を本文から
計算している（`Linker.first_positions()` と `Document.locate_at()`）。座標を足すと
それが**動き**になる。**保存しない**規律もそのまま効くので、版管理も補正も要らない。

### 本格的な GIS は要らない

歴史戦記のイフものだと**実在の地図が存在しない**のが普通（架空の大陸に緯度経度は無い）。
必要なのは**「1 枚の絵の上に点と線を置く」だけ** —— 画像を 1 枚置いて、その上の
相対座標（0〜1）で持つ。投影法・座標系・GeoJSON・タイルは要らない。

相関図で**力学モデルを避けたのと同じ判断の形**（決定的に置ける手段があるなら重い道具を
入れない）。実在の地図でも同じ仕組みが使える —— 背景画像が地図の画像になるだけ。

### 描画のライブラリも要らない（自前がいちばん軽い）

**要るものは全部この家にある。**

| 要るもの | 既にあるもの |
| --- | --- |
| 拡大縮小・移動 | `graph.js` の `viewBox` 操作（掴み・ホイール・−／全体／＋・矢印キー） |
| 線を引く・押させる | `.rel-edge` / `.rel-edge-hit` / `.hot` / `.lit` 一式 |
| 押したら編集 | 辺のダイアログ（`index` と `rel_to` で書き手へ辿る） |
| 説明を出す | `installDetail()`（図の下の高さ固定の枠） |
| 枠に収める | `boundsOf()` / `{ root, box }` |

しかも**地図は配置を計算しない**（座標が与えられる）ので、`orderRows()` も
`placeLabels()` も `arcSides()` も要らない。**5 つの見せ方の中でいちばん実装が小さい**
可能性がある。

**画像は svg の中に `<image>` として置く。CSS の背景にしないこと** —— `viewBox` を
動かす方式なので、中に入れれば**画像と線と語が一緒に動く**。背景にすると 2 つを別々に
動かす同期処理が要り、`graph.js` の資産が使えなくなる。座標変換も要らない（相対座標に
絵の寸法を掛けるだけ）。

**Leaflet が意味を持つのは、実在の地図タイルを引くと決めたときだけ。** 軽い部類
（依存ゼロ・数十 KB）で、`L.CRS.Simple` + `L.imageOverlay` は画像 1 枚を座標系にする
架空地図向けのモードまである。だが辺を `Polyline` で描き直すことになり、
**`.rel-edge-hit` も `.hot` / `.lit` も `installDetail()` も編集ダイアログの繋ぎ込みも
全部が別実装**になる ——「見せ方ごとに別の道を作ると『片方だけ拡大できない』が起きる」
そのもの。**タイルを引くと決めるまでは入れない。**

### 地図の SVG は通せる（ペルソナの規則をそのまま当てない）

**弾いていたのは「中身を検査せずにそのまま返す口」であって、SVG という形式ではない。**
このリポジトリは相関図の 5 つの見せ方すべてで SVG を出している —— **自分で組み立てた
もの**だから何の問題も無い。危険なのは**出所と出し方**。

**地図では通す価値がある。**「拡大縮小は `viewBox` を動かす。CSS の `transform` に
変えないこと —— にじむと SVG の意味が無い」と決めてあるのに、**背景だけラスタにすると
その原則と正面から衝突する**（線とラベルは鮮明なまま地図だけボケる）。地図は線画で、
拡大が本質。

**条件は 2 つ。どちらも安い:**

- **`<image>` に埋め込む。** ブラウザは `<img>` / `<image>` 経由で読んだ SVG を
  **secure static mode** で描くので、中の `<script>` も `onload` も外部参照も**動かない**。
  仕様レベルの保証で、サニタイズより堅い。しかも上に書いた置き方がそのままこれに当たる
- **配る口に `Content-Security-Policy: sandbox`。** 埋め込みだけだと穴が 1 つ残る ——
  **URL を直接開かれたとき**は画像ではなく文書として扱われ、スクリプトがこちらの
  オリジンで動く。ヘッダ 1 行でそこも opaque origin に落ちる（`nosniff` も一緒に）

**サニタイズで通す道は採らない。** `htmlclean` の許可制を広げると**2 つめの
サニタイザ**を持つことになり、しかも SVG は面が広い —— `<foreignObject>` で HTML を
埋められ、`<use href>` が外部を引け、`<set>` / `<animate>` で**属性を後から立てられる**。
上の 2 つで足りるなら増やす理由が無い。

**ペルソナは現状のまま**（ラスタのみ）。同じ理屈は効くが、**顔は拡大しない**ので口を
作り替えてまで払う理由が薄い。**規則が「何を出す口か」で分かれる**ことになるので、
揃えたくなったらこの段落を読むこと。

### 守ることになるもの

- **「座標が書いてあるものが地図に出る」。分類しない。** 種別やタグで「どれが地名か」を
  持つと、**分類の漏れがそのまま図の欠落**になる。座標を書いた＝出したいという意思表示
  なので機械が推測する余地がない ——時系列の「判明位置が書かれているかで切る。これが
  嘘をつかない唯一の線引き」とまったく同じ考え方。
  なお現状 `EXTRACT_KINDS` では地名は `proper`（固有名・独自語）に入っていて独立して
  いないが、**独立させる必要はない**（上の理由で分類を鍵にしないため）
- **出せなかったものは数える。** 座標の無い地名、範囲外に落ちた辺。
  `hidden` / `outside` / `undated` と同じ約束で、黙って欠けた図を出さない
- **実在の地図タイルを引くなら、外部通信の約束に触る。** タイルは**読んでいる場所
  そのものを配信元へ送る**（どの地名を見ているかが漏れる）。やるなら**利用者が明示的に
  選んだときだけ + 画面に書く** —— 読み上げのオンライン音声（`🌐` と注意書き）と同じ扱い。
  **画像 1 枚方式なら通信ゼロ**なので、そちらを既定にする

### 絵そのものをどうするか

描画より先に、**その絵が何なのか**を決める必要がある。

- **絵は利用者が持ち込む。描く道具は作らない。** GlossPop は辞書の道具であって
  お絵描きソフトではない。**明記しておかないと、後から「線を引けるように」が足される**
- **絵は前提にしてよい。** 座標の入力が「地図の上に置く」である以上、絵が無ければ
  座標は書けない（無地の平面に置かせることはできるが、**何を目印に置くのか**が無い）。
  絵の無い辞書では地図を選べない —— **時系列とまったく同じ前例**（選べないときは
  黙って別の図に差し替えない・注意書きを出す・覚えている選択は書き換えない）
- **辞書に複数枚。名前で識別する。**「桶狭間の局地図」と「東海道全体図」が同じ辞書に
  共存する。ペルソナは**決め打ちの名前**で逃げられたが、**地図は逃げられない** ——
  7 番（用語ごとの画像）とまったく同じ問題で、組み立てた結果が辞書の中に収まっているかを
  最後に検査する形（控えの `_backup_path` と同じ）になる
- **座標は絵の幅を 1 とした比で持つ。** 縦横それぞれに 0〜1 を割り当てると、**縦横比の
  違う絵に差し替えたとき点が歪む**。幅基準なら、同じ地図の高解像度版への差し替えで
  点は動かない
- **どの絵を出しているかを図に必ず書く**（相関図の範囲と同じ約束）
- **こちらが配る絵だけ権利を気にする。** 国土地理院の地図にも OSM のタイルにも利用規約が
  あり、スクリーンショットの同梱は避ける。**`samples/` に入れるならパブリックドメインの
  古地図か自作**。利用者が自分で用意するぶんは自由

### 日記の用途は後回しでいい

地名に日付が付いて、時系列と地図で自分の足取りを振り返る形。同じ仕組みには乗るが、
**「読んだものから抽出する」という主動線から外れる**（日記は自分で書くもの）。
先に架空世界の地図をやって、日記はその応用として後から。

### 学術用途（諸説の並記）—— 座標はエントリに固定できない

**提起された使い方**: 桶狭間の戦い。信長の進軍ルートは確定していないが、説はいくつか
ある。説ごとに配置を切り替える、あるいは全部を重ねて出す。読むのは教科書的なテキストで、
**説ごとの書き換えは本文ではなく辞書の側でやる。**

**この使い方は、上に書いた前提を 2 つ壊す。**

**1. 「新しく要るデータは座標 1 つだけ」が成り立たない。** 上は*地名エントリの
frontmatter に座標*を置く前提で、進軍経路は地名どうしの関係だから `relations` で足りる、
と書いた。だが**人物の位置は事件と説に依存する** —— 信長の座標は「桶狭間・A説」の中でしか
決まらず、`信長.md` には書けない。人物エントリは時代をまたいで語られるので、
**そちらが主軸で、位置は従**。必要なのは 事件（説）→ 人 → 位置 の 2 段階で、
**座標はエントリではなく関係につく。**

**2. 時間が別物。** `timeline.py` の「位置は計算する。保存しない」は、**読者がいつ
読めるようになるか**（本文中の初出）を計算している。史実の 1560 年は本文から計算できず、
**人が書くしかない**。つまり**2 つの時間軸が併存する**。保存しても「ずれる」問題は
起きない（ずれるのは計算値と本文の対応であって、人が書いた値ではない）が、
**時系列の図がどちらで並べるのか**という選択が新しく生まれる。

### 座標抜きでも骨格は今日動く

地図と座標を除けば、この構想の形は**既存の機能でそのまま作れる**。実装を決める前に、
まずここまでで使えるかを確かめられる:

- 説をエントリにして、事件から `relations` で張る（`label` に「別働隊」、`rank` で上下）
- 教科書テキストを読みながら「桶狭間の戦い」に自動リンク
- `ego.js` で事件を中心に据えると、**1 つ先が説・2 つ先が人物**
- `matrix.js` の 説 × 人物 で「この説はこの人物に触れていない」が空きマスで読める

### 説はカテゴリよりエントリを推す

提起では説ごとにカテゴリを作る案だった。**カテゴリは辞書に対してフラット**なので、
そうすると **事件 × 説の直積**になる（「A説」は事件ごとに意味が違うので使い回せず、
「桶狭間・迂回奇襲説」が事件の数だけ増える）。絞り込みの選択肢がそれで埋まる。

カテゴリ「説」に説エントリを置くほうが 3 つ噛み合う:

- **2 段階が `relations` でそのまま書ける** —— 説 → 人 の関係に位置と時刻が載る。
  **新しいデータ型を作らずに済む**
- **`ego.js` の半径 2 がちょうど収まる** ——「相手の相手＝自分では書いていない繋がり」
  という半径 2 の理由とも合う
- **`matrix.js` の空きマスが効く** ——「無い」を見せるために足した見せ方が、
  ここでは主役になる（どの説がどの人物に触れていないか）

**代償**: 「桶狭間の戦い」を押したときに諸説がアコーディオンで並ぶ形は失われ、
関係を辿る形になる。

### 実際に作った（`samples/戦国時代/`）

**机上ではなく実物で確かめた。** 22 語 34 関係で、`tests/test_samples.py` が
そのまま通る —— **点検が黙り、全表記が実際にリンクになり、関係が全部解決する**。
**座標を除けば、今日のスキーマに何も足さずに書ける**ことが実証できた。

```
samples/戦国時代/
  桶狭間の戦い.md  姉川の戦い.md  本能寺の変.md   ← 戦いごとに 1 ファイル
  .glosspop/
    style.md                    「淡々と。確定していないことは断定しない」
    categories.yaml             事件 / 説 / 人（陣営はサブカテゴリ）/ 地
    glossary/
      事件/ 3 件                ← 説に依らない事実
      説/   2 件                ← その説でだけ言えること（桶狭間の進軍路だけ）
      人/   9 件                ← 戦いが増えても割れない・太らない
      地/   8 件
```

**時代や分野をカテゴリにしない。カテゴリは種別（事件 / 説 / 人 / 地）。**
「戦国時代」は**フォルダの名前**で、辞書はフォルダに付いてくるのだからそこが単位になる。
時代をカテゴリにすると、(1) カテゴリ絞りが軸の切り替えになる性質を失い、
(2) 「本能寺」（地）と「本能寺の変」（事件）のような**種別違いの併存**が使えず、
(3) 一覧の見出しが 1 つしか出ない。陣営は**サブカテゴリ**（ディレクトリにならないので、
家中を移ってもファイルが動かない）、テーマは**タグ**。

**説は「桶狭間.md の中の項目」ではなく、それ自体が 1 ファイル。** 理由は 1 つで、
**関係の起点になれるのはエントリだけ**だから（`relations` は
[`EntryBase`](../glosspop/core/models.py) が持つ）。説を事件ファイルの中の一項目に
すると、**説 → 人 の関係を書く場所が無く**、2 段階が表せない。

**今日との差は 1 か所だけ。** `Relation` は `to` / `label` / `back` / `rank` / `reveal`
の 5 項目で、**足りないのは位置と時刻の 2 つ**。(b) 案はここに項目を増やすことを指す。

#### 作って初めて分かったこと

- **説に依らない事実は「事件」が持つ。説が持つのは「その説でだけ言えること」。**
  最初は 事件 → 説 だけにしたが、**それだと今川義元が中心の図に出てこなかった**
  （`ego.js` の半径 2 に対して 3 ホップ。事件から見れば主役なのに）。当事者が誰かと
  決着の地は**どちらの説を採っても動かない**ので、事件の側に置くのが正しい。
  直したら 1 ホップに来た
- **`term` に事件名を含めない。** 「桶狭間・迂回奇襲説」にすると**本文にその表記が
  現れず**、`test_every_surface_appears_in_the_document` が落ちる ——「登録したのに
  リンクにならない」そのもの。**見出しは本文の表記**（「迂回奇襲説」）で、これは
  「多く使われているほうを見出しにする」という既存の作法どおり。事件名込みが要るのは、
  同じ辞書に別の事件の同名説が入ったときだけ
- **`rank`（上下）は説 → 人 には無い。陣営の中の上下は別軸**で、人 → 人 に書く。
  実データでも **説 → は全部空、人 → 人 だけが `下` / `対等`** になった。
  **混ざらないのは関係を起点のエントリが持つから** —— 軸を分ける仕組みを新しく足す
  必要は無く、**カテゴリで絞れば軸が切り替わる**（[`build_graph`](../glosspop/core/relations.py)
  は範囲内のエントリの `relations` しか走査しないので、「人」で絞ると説エントリごと
  外れて主従だけの図になる。説ノードが `outside` で足されることもない）
- **上下がはっきり書けないなら空でよい。** `RANK_OPTIONS` の先頭は「上下は指定しない」
  で、段が立つのは**書いてあるものだけ**（「分類しない。書いてあるものが出る」と
  同じ線）。史料で確定しない主従を無理に埋めさせる仕組みは要らない。
  **仮に上下自体が説で割れるなら**、それも同じ形で説の側に書ける
- **人物側のファイルには何も書かない。** 向きの基準は「自分から `to` を見て」に
  固定してあるので、説 → 人 の一方向で統一する（相互は `back` で 1 本にする。
  2 本に割ると二重に持つことになる）
- **行列がそのまま「説の比較表」になった。** 太子ヶ根は迂回奇襲説だけ、中島砦は
  正面攻撃説だけ、田楽狭間と織田信長は両方 —— **「無い」を見せるために足した
  見せ方が、ここでは説の違いを読む道具になる**
- **戦いを足しても人物のファイルは太らない（実測）。** 織田信長は 3 つの戦い全部に
  出るが、`織田信長.md` に書かれている関係は **7 本**（全部 人 → 人 の間柄）で、
  戦いからは **5 本指されているだけ**。関係は起点のエントリが持つので、事件が増えても
  増えるのは事件側のファイル。読めなくなることもない ——
  [`backlinks()`](../glosspop/core/relations.py) が用語ページに
  **「この語を指している側」**として出す
- **文書を分けると図が戦いごとに絞れる（実測）。** 同じフォルダに 3 ファイルを置くと、
  `?doc=` の図は **桶狭間 11 語 / 姉川 9 語 / 本能寺 7 語**。信長はどれにも出る。
  **新しい仕組みは要らない** —— 本文を 1 ファイル足すだけで絞り込みが付いてくる。
  範囲外に落ちた辺は `outside` で数が返る（姉川で 8 本）ので、黙って欠けない
  - **ただし本文で他の戦いに言及すると、その戦いも図に入る。** 姉川の本文が
    「桶狭間の戦いでは今川方として……」と書いているので、姉川の図に「桶狭間の戦い」が
    出る。`entries_in()` は本文に出る語を拾う仕様どおりだが、「この戦いの図」としては
    余計。**言及＝出てくる、なので避けようがない**（絞りたければ本文の書き方で調整する）
- **「時期で立場が変わる」は書けるが、`rank` に時間は無い。** 徳川家康は**自分では
  1 本も書いていない**のに 4 方向から指される —— 桶狭間（今川方として従軍）/
  姉川（織田方として加わる）/ 今川義元（`rank` 上）/ 織田信長（`rank` 対等）。
  **上位が 2 つ同時に立つ**が、どちらも別の時期の事実。図は時間を持たないので両方出る。
  **これは 9 番の時系列（判明位置＝読者がいつ読めるか）とは別の時間軸**で、
  埋めるなら **(b) の「時刻」がそのままここに効く** —— 座標より先に時刻のほうが
  要る場面がある、というのは作るまで見えていなかった

#### (a) と (b) が排他でないことの実証

**田楽狭間がどこにあるかは説に依らない**（地名エントリの座標 = (a)）。
**信長がそこへどう至ったかは説による**（説 → 地点 の関係 = (b)）。
同じ辞書の中で**両方が要る**ので、どちらかを選ぶ問いではない。

### 守ることになるもの（既存の約束から自動で決まる）

- **参照は名前のまま。ID を導入しない。** 2 段階になっても吸収は `relations.resolve()`
  の 1 か所（迂回して自前の照合を書かない）
- **どの説を出しているかを必ず画面に書く。** 全部重ねて出すとき、線がどの説のものか
  分からないと**図が嘘をつく** —— 相関図の範囲（辞書全体 / この文書）と同じ約束
- **座標が書いてあるものが地図に出る。分類しない**（上と同じ）。ただし判定の単位が
  エントリではなく**関係**に移る
- **出せなかったものは数える**（座標の無い人物、範囲外の辺）

### どこに作るか —— 3 つめの道具になりうる

サーバ配置とアカウント別のアクセス制御は GlossPopApp の領域だが、**あちらは
コンシューマ（Web 小説）に決めたばかり**（→ [mobile-rethink.md](mobile-rethink.md)）。
学術路線を足すと、「社内共有路線とデコ路線は同じアプリになりにくく、**捨てるものの
一覧が主役の選び方で変わる**」で一度やった選び方をもう一度やることになる。
**同じシステムに載せるかは未決**で、3 つめの道具になりうることも含めて保留。

**実装は後。順番は「地図が先、学術用途はその後」**（提起者の判断）。**座標の持ち主**
(a)(b)(c) は、実際に絵の上へ点と線を置いてみないと決め手が出ない —— 机上で選ばない。

**ただし説の持ち方だけは今日試せる**（座標を除けば既存のスキーマで書ける。→ 上）。
地図を待たずに形の当たりは取れる。

### 最小の一歩（`relations` を 1 項目も変えずに地図が出る）

1. **絵を 1 枚置く**（配る口はペルソナと同じ規則）
2. **地名エントリに座標**（frontmatter・(a)）
3. **`draw()` に分岐を 1 つ足す**（`{ root, box }` を返す。他の 5 つとまったく同じ枠）
4. **地名どうしの関係を、そのまま線で引く**
5. **座標の無い語・範囲外の辺を数えて出す**

**core を触るのは (b) が要るとき**、つまり人の位置＝学術用途へ進むときだけ。

### GlossPopApp との切り分け（着手前に見るところ）

**この構想のいちばん大きい部分は、持っていく作業が発生しない。** 座標を `Relation`
（または `EntryBase`）に足すということは、変更先が
[`glosspop/core/models.py`](../glosspop/core/models.py) —— **core は GlossPopApp が
丸ごと借りている**ので、書いた瞬間に向こうへ効く。`build_graph()` が座標を返すように
するのも core。

**描画はもともと共有していない**（`graph.js` / `ego.js` は本体だけで、GlossPopApp は
自前の `static/graph.js` で中心の図を書いている）。共有するのは `graph-model.js` の
**形の規則**だけで、しかも**地図は配置を計算しない**（座標が与えられる）ので、
そこへ足すものもほとんど無い。

**割れるのは 2 つ。**

- **背景画像の置き場所と配る口。** `store` / `config` の領域なので **core に入らず
  書き直しになる**（本体は `<辞書>/images/…`、向こうは利用者ごと）。ただし**規則は
  ペルソナの顔で両方が既に持っている** —— パスを外から受け取らない・SVG は通さない・
  拡張子は中身から決める・上限を持つ・URL に更新時刻。新しく考えることは無く、
  当てはめるだけ
- **zip に画像を含めるか。ここがいちばん鋭い。** `archivefmt` は core なので
  **両者で必ず同じ形**になる。片方だけ画像を入れると、GlossPopApp の「控えは GlossPop と
  往復できる」が壊れ、しかも **zip は読めてしまって一部だけ落ちる**（例外にならないぶん
  気付きにくい、といつも書いている壊れ方そのもの）。本体側には「含めるのは全体の辞書と
  カテゴリマスターだけ。増やすなら消える範囲が広がることを UI に出す」という明文の規則が
  あるので、**足すなら両方同時に決める**

**手順**:

1. **最小の地図は (a) だけで通る**（地名エントリに座標）。`relations` を変えないので、
   **この段階では core を触らない = 向こうへ何も波及しない**
2. **本体で地図の見せ方を作り、実際に置いてみる**
3. **(b) を足すのは学術用途へ進むとき**（人の位置）。**ここで初めて core が動き、
   同時に GlossPopApp へ効く**
4. **画像の置き場所と zip の扱いは、2 で形が固まってから両者同時に決める**

4 を先にやると、**まだ形の分からないものに対して往復の約束を決める**ことになる。

**地図は携帯で 3 つめの見せ方になりうる。** [mobile-rethink.md](mobile-rethink.md) の表
では中心の図と時系列の 2 つだけが「効く」だが、**地図は画像 1 枚に点を置くだけで横幅を
前提にしない**。なりうるかは実物を見てからだが、その目で作っておく価値はある。

### 決めていないこと

- **座標を誰が持つか。3 案あるが、選択肢ではなく役割が違う**（どれか 1 つを選ぼうと
  しないこと）。
  **(a) エントリの frontmatter** —— 地名は場所そのものなので、これが自然。
  **最小の地図は (a) だけで通る**。
  **(b) 関係の項目** —— 人は事件ごとに動くので**こちらにしか書けない**（説 → 人 に
  1 点ずつ）。学術用途で要る。
  **(c) 新しい型**（事件エントリが (人・時刻・座標) の並びを持つ）—— **進軍の軌跡**が
  書けるが拡張がいちばん大きい。**(b) で軌跡が書けないかを先に試すこと** ——
  進軍経路はもともと**地名エントリどうしの関係**なので、説 → 地点 を順に並べれば
  足りるかもしれない。
  変えると `.claude/skills/gloss-add/SKILL.md`・MANUAL・`base.js` まで波及する
- **座標をどうやって書くか。** `0.42, 0.31` は人が frontmatter に手で書ける値ではない
  ので、**地図の上に置く UI が実質必須**。「新しく要るデータは座標 1 つだけ」の見た目
  より、実装はここで一段大きくなる。
  なお相関図で「ノードを掴んで動かす」を捨てた理由は**「座標を書く場所を作ると
  『エディタで直接編集してよい』が崩れる」**だった（→ [design-notes.md](design-notes.md)）。
  地図はまさにその場所を作るので、**地図だけが座標を持ってよい図**になる ——
  掴んで動かす仕組みも、ここでは正当化される
- **どの絵の上の座標なのか**を併せて持つ必要がある（1 枚の絵に対する相対座標のため）
- **絵をどこに置くか。** 用語ごとの画像（→ 7 番）と同じ規則になるはずだが、あちらは
  エントリ 1 件に 1 枚、こちらは辞書に数枚（地方ごと・時代ごと）で単位が違う
